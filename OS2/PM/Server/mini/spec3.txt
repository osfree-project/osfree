# Часть II. Роль сервера и пять уровней

## II.1. Роль сервера в системе

**FreePM — распределённая реализация Presentation Manager.** Приложение, слинкованное с PMMERGE/PMGPI, работает через локальные клиентские DLL; фактическое состояние PM и рендеринг выполняются в отдельном процессе `PMSERVER.EXE`.

| Сторона | Компонент | Роль |
|---|---|---|
| Клиент | Приложение | вызывает `Gpi*`/`Win*` |
| Клиент | PMMERGE.DLL | прокси `Win*`, `WndProc`-прокси, `WinInitialize` |
| Клиент | PMGPI.DLL | прокси `Gpi*` |
| Клиент | PMCLIENT.DLL | keepalive, reconnect, wire-транспорт (7 экспортов `Fc_Ses*`) |
| Транспорт | PMTCP.DLL (или PMPIPE/PMEHSHM) | backend: `Fc_Trn*` (ord 1–7), `Fs_Trn*` (ord 8–11) |
| **Сервер** | **PMSERVER.EXE** | **авторитетное состояние PM: процессы, потоки, соединения, HAB, PS, WND/MQ/DC (Phase 4+), GOCA-поток, рендеринг** |

**Ключевой архитектурный принцип:** сервер — **единственный авторитетный владелец** состояния PM. Клиент хранит только opaque-хэндлы (`HAB`, `HPS`, `HWND`), выданные сервером, и передаёт их как аргументы. Никакого клиентского PS, WND, MQ в мини-сервере нет.

**Сервер — не библиотека и не встраиваемый модуль.** Это отдельный процесс с собственным жизненным циклом (§XIII.1), запускаемый клиентом по требованию.

## II.5. Границы

**Клиент / сервер:** wire-протокол (§IV). Клиент не знает про `Fs_Hab`, `GPI_PS`, `GOCA_CTX`, `Gre*`. Сервер не знает про `PMMERGE`, `PmcSendCommand`.

**Сервер / GRE:** контракт `Gre*` (§II.9). Сервер не знает про устройство вывода; GRE не знает про GOCA-поток, сегменты, элементы.

**GPI / WIN:** оба класса принимают wire-команды в `Fs_Server`, но диспетчеризуются в разные методы. Между собой не пересекаются, кроме `GPI_PS::m_hHab` (back-ref).

**PS / HDC / HWND / Media:** PS создаётся из **HDC**, а не из HWND. HDC — источник, HWND — один из способов его получения. Без HWND (включая `HWND_DESKTOP`) пиксели на экран не выводятся: memory DC (`DevOpenDC(OD_MEMORY)`) даёт только offscreen-рисование.

| Фаза | `goca.hdc` | HWND нужен? | Что рисуется |
|---|---|---|---|
| P0 (текущая) | `NULL` | Нет | Ничего (все `Gre*` — заглушки). GOCA-поток, сегменты, bookkeeping работают |
| Step K (P1) | HDC от клиента (после `NGpiAssociate`) | Нет | Ничего на сервере (клиентский HDC) |
| Phase 4 (P4) | memory DC (`DevOpenDC(OD_MEMORY)`) | Нет | Offscreen в `pVBuffmem`; визуально — ничего |
| Phase 6 (P4.5) | screen DC (`WinOpenWindowDC(HWND_DESKTOP)` / `WinGetScreenPS(HWND_DESKTOP)`) | **Да** | **Реальный экран** |

`HWND_DESKTOP` — предопределённое символическое имя (`0x00000001` в `PMWIN.H`) для **реального** окна рабочего стола, которое PM создаёт при старте (IBM PM Ref Vol.1: «PM creates at start-up a window known as the desktop window»). Не «псевдо-HWND».

```

                 case NGpiLine:

                           uPos = 0
                           while (uPos < cbStream):
                             cbOrder = GocaOrderLength(c, p, cbAvail)
                             oc = p[0]
                             switch (oc):

                                 nPts = len / pointSize
```

**Ключевое:** для `GCLINE` — **лишний `GreGetCurrentPosition`** в `DoLine` (`RefreshCurPos`). Позиция уже в `c->ptlCurPos`. Это **баг Extra** (§XI.11).

### DM_RETAIN

```
GpiLine(hps, pt)

  SrvDeliver(ps, buf, len):
    if (ps->lOpenSeg == 0): нет (сегмент открыт)
    am = ps->ulDrawingMode                     // DM_RETAIN
    if (!(ps->ulInitialSegAttrs & SEGATTR_BIT(ATTR_CHAINED)))
```

**Ключевое:** GRE не вызывается. `goca.lb/cb/mb/ab` **не обновляются** (это корректно per N1 — атрибутные Query в DM_RETAIN недействительны).

### DrawSegment

```
NGpiDrawSegment(hps, 1):
  GpiPsGocaFindSeg(ps, 1, &start, &end):
    off = 0
    while (off < cbGoca):
      cb = GocaOrderLength(...)
      if (p[0] == OCODE_GBSEG && cb >= 6):
        name = GocaGetU32(c, p + 2)
        if (name == lSegId):
          start = off
          end = cbGoca
          off += cb
          while (off < cbGoca):
            cq = GocaOrderLength(...)
            if (q[0] == OCODE_GBSEG): end = off; break
            off += cq
          return TRUE
      off += cb
  ps->goca.pbStream = ps->pbGoca + start
  ps->goca.cbStream = end - start
  GocaParseStream(&ps->goca)
```

**Ключевое:** `GocaParseStream` получает **весь** диапазон, включая `GBSEG`. Парсер видит `OCODE_GBSEG` → `case OCODE_GBSEG: break;` (no-op). Дальше парсит тело.

```
        if (q[0] == OCODE_GBSEG): end = scan; break
        scan += cq
      if (!pfn(ps, name, start, end, f1, f2, pUser)): return TRUE
      off = end
    else: off += cb
```

`SrvCbDrawChain`: фильтр (не invisible, не dynamic, не unchained) → `SrvReplaySegment(ps, start, end)`:
```
ps->goca.pbStream = ps->pbGoca + start
ps->goca.cbStream = end - start
GocaParseStream(&ps->goca)
```

## II.9. Контракты между слоями

### GPI ↔ GOCA

| Направление | Что | Контракт |
|---|---|---|
| GPI → GOCA (emit) | `GocaEmit*(&ps->goca, buf, cb, ...)` | Возвращает `len >= 0` или `GPI_ALTERROR`. `buf == NULL` → возвращает `need`. **Не обновляет** `ps->goca.lb/cb/...`. |
| GPI → GOCA (parse) | `SrvParseOrder(ps, p, cb)` → `ps->goca.pbStream = p; ps->goca.cbStream = cb; GocaParseStream(&ps->goca)` | `GocaParseStream` **обновляет** `ps->goca.lb/cb/mb/ab`, `ptlCurPos`, `lError`. Возвращает `GOCA_OK` или `GOCA_ERR_*`. |
| GPI ← GOCA | `GocaOrderLength(&ps->goca, p, cb)` | Возвращает длину ордера (1/2/2+LEN/4+U16). 0 = truncation. |
| GPI ← GOCA | `GocaGetU32(&ps->goca, p + 2)` | Читает `GBSEG.Name` с учётом endian. |
| GPI → GOCA (format) | `GocaSetFormatFromOptions(&ps->goca, flOptions)` | Устанавливает `coordSize`/`coordEndian` из `PS_FORMAT_MASK`. |

**Правило:** `GocaEmit*` — только кодирование; `GocaParseStream` — единственное место, где registers обновляются. В DM_RETAIN registers **не** обновляются (per N1). GPI не парсит GOCA вручную, кроме `GocaOrderLength`/`GocaGetU32` для чтения метаданных (`GBSEG.Name`).

**N4 в контексте HWND:** `(HDC)hps` — бессмысленный HDC (указатель на PS выдан за HDC). Правильная последовательность по фазам:
- **P0** — `GpiPsCreate(hps, NULL, flOptions)` → `goca.hdc = NULL`. Все `Gre*` — заглушки; работают GOCA-поток, сегменты, bookkeeping.
- **Step K** — `NGpiAssociate(hdc)` → `goca.hdc = hdc` (клиентский; на серверном экране ничего не видно).
- **Phase 4** — сервер создаёт **memory DC** (`DevOpenDC(OD_MEMORY)`) → offscreen-рендеринг в `pVBuffmem`; визуально ничего.
- **Phase 6** — сервер получает **screen DC** (`WinOpenWindowDC(HWND_DESKTOP)`) → визуальный рендеринг.

### GOCA ↔ GRE

| GOCA | GRE | Контракт |
|---|---|---|
| `DoLine` | `GrePolyLine(c->hdc, pptl, n)` | `c->hdc` — заимствованный HDC. Если `NULL` — GRE вернёт ошибку; парсер не проверяет. |
| `DoGSCP` | `GreSetCurrentPosition(c->hdc, &pt)` | Обновляет `c->ptlCurPos`. |
| `GocaSetAttr` | `GreSetAttributes(c->hdc, lPrim, 0, flAttrs, &bundle)` | `bundle` — указатель на `c->lb/cb/mb/ab`. |
| `GocaInit` | `GreGetAttributes(c->hdc, lPrim, mask, &bundle)` | Заполняет `c->lb/cb/mb/ab` из устройства. |
| `GocaInit` | `GreGetCurrentPosition(c->hdc, &c->ptlCurPos)` | Начальная позиция. |

**Правило:** GOCA не знает, что `c->hdc` — линк к Media. Он просто передаёт его в GRE. GPI устанавливает `c->hdc` через `NGpiAssociate` (Step K). Сейчас — `GocaInit((HDC)hps, ...)` в `GpiPsCreate` — **N4** (§XI.9).

### Клиент ↔ Сервер

| Направление | Что | Контракт |
|---|---|---|
| Клиент → Сервер | `Fc_SesPostCommand(cmd, data)` | `cmd = F_CMD_MAKE(class, opcode)`. `data` — primary argument. |
| Клиент → Сервер | `Fc_SesPostData(&cbArgs, 4)` | Длина args. |
| Клиент → Сервер | `Fc_SesPostData(args, cbArgs)` | Args. |
| Сервер → Клиент | `m_pfnSend(&resp, 16)` | `FPM_RESP_HEADER`. |
| Сервер → Клиент | `m_pfnSend(pArgs, cbPayload)` | In-place payload. |
| Сервер → Клиент (HAB sync) | `m_pfnSend(&ulResult, 4)` | Только `ulResult`, 4 байта. |
| Клиент ← Сервер | `Fc_SesGetData(&resp, &len, 16)` | Header. |
| Клиент ← Сервер | `Fc_SesGetData(pArgs, &len, cbPayload)` | Payload. |
| Клиент ← Сервер (sync) | `Fc_SesSendCommand(cmd, data)` | Внутри: `PostCommand` + `GetData(4)`. |

**Правило:** `pArgs` на клиенте и сервере — **один и тот же буфер** (логически). Сервер мутирует in-place, возвращает через `cbPayload`. `ulLastError` — **не используется** (всегда 0). `ulStatus` — 0 = ok, не-0 = транспорт/ошибка.

## IV.1. Формат команды

```c
#define F_CMD_CLASS_MASK      0xFFFF0000UL
#define F_CMD_OPCODE_MASK     0x0000FFFFUL

#define F_CMD_CLASS_CORE   0x0000
```

## IV.2. Классы и диспетчеризация

## IV.3. Поток сообщения (async — GPI, не-HAB WIN, CORE)

```
Клиент:
  1. Fc_SesPostCommand(cmd, data)     // cmd + data → backend
  2. Fc_SesPostData(&cbArgs, 4)        // length prefix
  3. Fc_SesPostData(args, cbArgs)      // payload
  4. Fc_SesGetData(&resp, &len, 16)    // read header
  5. if (resp.cbPayload > 0)
       Fc_SesGetData(pArgs, &len, resp.cbPayload)  // read payload

Сервер:
  1. pm_handler(recvobj, ncmd, data, thread) → Fs_Server::HandleCommand
     - поиск pConn/pThread через m_conns.FindByRecvobj
     - классификация ncmd по F_CMD_GET_CLASS
  2. HandleGpiCall / HandleWinCall / HandleCoreCommand
     - m_pfnRecv(&cbArgs, 4)
     - m_pfnRecv(pArgs, cbArgs)
     - Dispatch…(…)
     - SendHeader (16 B)
     - if (cbPayload > 0) m_pfnSend(pArgs, cbPayload)
```

## IV.4. Поток сообщения (sync — HAB WIN, 0x0001–0x000F)

```
Клиент:
  1. Fc_SesSendCommand(cmd, data)
       → Fc_TrnPostCommand(cmd, data)          // 8 B
       → Fc_TrnGetData(&retcode, &l, 4)        // 4 B

Сервер:
  1. pm_handler → HandleCommand → HandleWinCall
     - fnCode в диапазоне 0x0001..0x000F
     - m_pfnRecv НЕ вызывается (cbArgs нет)
     - DispatchWinHab(pRecvobj, fnCode, data, NULL, 0, &cbPayload)
     - m_pfnSend(&ulResult, 4)                 // 4 B, без FPM_RESP_HEADER
```

**Контракт:** `(APIRET)-1` от `Fc_SesSendCommand` — транспортная ошибка. Иначе — `ulResult` (iHab для Initialize, BOOL для Terminate, `PMERR_*` для GetLastError). Функции `Fc_TrnSendCommand` (ord 5) и `Fc_TrnGetData` (ord 7) документируют `-1` как «сервер не может вернуть `0xFFFFFFFF` как бизнес-значение».

## IV.5. GPI class — точный байтовый layout

Для `GpiLine(LONG coords)`:

```
Fc_SesPostCommand:
  offset 0: cmd = F_CMD_GPI(NGpiLine) = (0x0001 << 16) | 0x6F = 0x0001006F
  offset 4: hps
Fc_SesPostData:
  offset 0: cbArgs = 8 (ULONG LE)
  offset 4: ptlEndPoint.x (LONG LE)
  offset 8: ptlEndPoint.y (LONG LE)
Total per message: 8 + 4 + 8 = 20 B
Response: 16 + cbPayload
```

Для `GpiSetAttrs(PRIM_LINE, LBB_COLOR|LBB_TYPE, 0, &lb)`:

```
cmd = F_CMD_GPI(NGpiSetAttrs) = 0x0001007A
hps
cbArgs = 12 + 28 = 40
lPrimType = 1 (PRIM_LINE)
flAttrMask = 0x0041 (LBB_COLOR | LBB_TYPE)
flDefMask = 0
abBundle = LINEBUNDLE (28 B)
Total: 8 + 4 + 40 = 52 B
```

## IV.6. GORDER class — определён, но не используется

```c
#define F_CMD_ORDER(oc) F_CMD_MAKE(F_CMD_CLASS_GORDER, (oc))
```

**В `HandleCommand` нет ветки для `F_CMD_CLASS_GORDER`.** Не реализовано (P8).

## IV.7. Payload-семантика

- `cbArgs` — **входной** размер (клиент → сервер).
- `cbPayload` — **выходной** размер (сервер → клиент).
- `pArgs` — **один буфер** на клиенте и сервере (логически). Сервер мутирует in-place, возвращает через `cbPayload`.
- `cbPayload <= cbArgs` (сервер не может вернуть больше, чем получил).

## IV.8. Обработка ошибок

- `resp.ulStatus`: 0 = ok; не-0 = транспорт/ошибка.
- `resp.ulResult`: результат функции (`LONG`/`BOOL`/`HANDLE`).
- `resp.ulLastError`: **не используется** (всегда 0). `PMERR_*` не передаются (A6).
- `GPI_ERROR = 0`, `GPI_OK = 1`, `GPI_ALTERROR = -1`.

## IV.9. CORE-команды (session management и диагностика)

|---|---|---|---|

## V.2. `GpiDispatch`

```c
ULONG GpiDispatch(HPS hps, ULONG ulFnCode,
                  const void *pArgs, ULONG cbArgs,
                  ULONG *pulResult)
{
    struct FPM_RESP_HEADER resp;
    LONG   len;
    APIRET rc;
    ULONG  cmd;

    if ((ulFnCode & 0xFFFF0000UL) != 0) return 1;
    cmd = F_CMD_GPI(ulFnCode);

    rc = Fc_SesPostCommand(cmd, (ULONG)hps);
    if (rc) return rc;

    rc = Fc_SesPostData(&cbArgs, sizeof(cbArgs));
    if (rc) return rc;

    if (cbArgs > 0 && pArgs != NULL) {
        rc = Fc_SesPostData((PVOID)pArgs, cbArgs);
        if (rc) return rc;
    }

    len = 0;
    rc = Fc_SesGetData(&resp, &len, sizeof(resp));
    if (rc || len != (LONG)sizeof(resp)) return (rc != 0) ? rc : 1;

    if (resp.cbPayload > 0 && pArgs != NULL && cbArgs >= resp.cbPayload) {
        len = 0;
        rc = Fc_SesGetData((PVOID)pArgs, &len, resp.cbPayload);
        if (rc) return rc;
    }

    *pulResult = resp.ulResult;
    return (resp.ulStatus != 0) ? resp.ulStatus : 0;
}
```

**Контракт:** `pArgs` должен быть мутабельным, если `cbPayload > 0`. `GpiDispatch` не знает, что в `pArgs` — просто копирует обратно.

```c
GPI_PS g_psTable[GPI_MAX_PS];   // в gpi_entry.cpp

static inline PGPI_PS GpiPsFind(HPS hps)
{
    int i;
    PGPI_PS ps;

    if (hps == NULL) return NULL;

    // pointer case: hps может быть указателем в g_psTable (сервер)
    ps = (PGPI_PS)hps;
    if (ps >= g_psTable && ps < g_psTable + GPI_MAX_PS && ps->inUse)
        return ps;

    // handle case: поиск по .hps
    for (i = 0; i < GPI_MAX_PS; i++) {
        if (g_psTable[i].inUse && g_psTable[i].hps != NULL &&
            g_psTable[i].hps == hps)
            return &g_psTable[i];
    }
    return NULL;
}
```

## VI.5. `DispatchWinHab` — sync-путь

```c
ULONG Fs_Server::DispatchWinHab(void *pRecvobj, ULONG fnCode, ULONG data,
                                 PBYTE pArgs, ULONG cbArgs, PULONG pcbPayload)
{
    Fs_Connection *pConn   = m_conns.FindByRecvobj(pRecvobj);
    Fs_Thread     *pThread = pConn ? pConn->GetThread() : NULL;
    Fs_Process    *pProc   = pThread ? pThread->GetProcess() : NULL;

    (void)pArgs; (void)cbArgs;
    if (pcbPayload) *pcbPayload = 0;

    switch (fnCode) {
    case NWinInitialize:
        /* data = tid */
        if (!pProc || !pThread) return 0;
        if (data == 0) return 0;
        if (pThread->GetHab() != NULL) return 0;   // already has HAB
        if (!m_habs.Create(pProc->GetIdClient(), data, &iHab)) return 0;
        pThread->SetHab(m_habs.FindByIHab(iHab));
        return iHab;

    case NWinTerminate:
        /* data = hab, используется только в strict-режиме */
        if (!pProc || !pThread || !pThread->GetHab()) return 0;
        iHab = pThread->GetIHab();
        if (m_cfg.fStrictHab && data != iHab) return 0;
        if (!m_habs.Destroy(pProc->GetIdClient(), pThread->GetTid(), iHab)) return 0;
        pThread->ClearHab();
        return 1;

    case NWinGetLastError:
        /* data = hab, используется только в strict-режиме */
        if (!pThread || !pThread->GetHab()) return PMERR_INVALID_HAB;
        iHab = pThread->GetIHab();
        if (m_cfg.fStrictHab && data != iHab) return PMERR_INVALID_HAB;
        return pThread->GetHab()->GetLastError();

    default:
        return 0;
    }
}
```

**Ключевое:** в не-strict режиме `data` не используется для поиска; HAB берётся у потока. `PMERR_INVALID_HAB = 0x104A` (из `F_platform.h`).

## VI.7. `SrvDeliver` — полное дерево решений

```c
static BOOL SrvDeliver(PGPI_PS ps, const BYTE *p, ULONG cb)
{
    ULONG am;

    if (!ps || !p || cb == 0) return FALSE;

    // 1. Нет открытого сегмента → сразу parse (DM_DRAW / Micro)
    if (ps->lOpenSeg == 0) {
        SrvParseOrder(ps, p, cb);
        return TRUE;
    }

    // 2. Есть открытый сегмент → решаем: retain / draw / both
    am = ps->ulDrawingMode;

    // 3. Unchained сегмент форсит DM_RETAIN
    if (!(ps->ulInitialSegAttrs & SEGATTR_BIT(ATTR_CHAINED)))
        am = DM_RETAIN;

    // 4. Retain
    if (PS_IS_RECORDING(am)) {
        if (!GpiPsGocaAppend(ps, p, cb)) return FALSE;
        if (!ps->bInElement && ps->ulEditMode == SEGEM_INSERT &&
            p[0] != OCODE_GBEL && p[0] != OCODE_GEEL)
            ps->lCurrentElement++;
    }

    // 5. Draw
    if (PS_IS_DRAWING(am)) {
        SrvParseOrder(ps, p, cb);
    }

    return TRUE;
}
```

**Проблема (баг #1):** `GpiPsGocaAppend` добавляет в конец `pbGoca`, а не в `uOpenSegEnd`. При редактировании не-последнего сегмента — ордер попадает в чужой сегмент.

**Проблема:** `DCTL_DYNAMIC` не проверяется (баг #5), `ulStopDraw` не проверяется (баг #4).

## VII.2. `GocaParseStream` — главный цикл

```c
LONG GocaParseStream(GOCA_CTX *c)
{
    c->uPos   = 0;
    c->lError = GOCA_OK;

    while (c->uPos < c->cbStream) {
        const BYTE *p       = c->pbStream + c->uPos;
        ULONG       cbAvail = c->cbStream - c->uPos;
        ULONG       cbOrder = GocaOrderLength(c, p, cbAvail);
        UCHAR       oc;
        LONG        rc;
        BOOL        bHandled = FALSE;

        if (cbOrder == 0 || cbOrder > cbAvail) {
            c->lError = GOCA_ERR_TRUNC;
            c->uErrOffset = c->uPos;
            c->uErrOrder = p[0];
            return c->lError;
        }
        oc = p[0];
        rc = GOCA_OK;

        if (c->pfnHandler)
            bHandled = c->pfnHandler(c, oc, p, cbOrder);

        if (!bHandled) {
            switch (oc) {
            case OCODE_GNOP1: case OCODE_GESD: case OCODE_GEPROL:
            case OCODE_GCOMT: case OCODE_GSGCH: case OCODE_GSMP:
                break;
            case OCODE_GSCOL: … break;
            …
            case OCODE_GBSEG: break;   // no-op
            case OCODE_VLONG: switch (p[1]) { … } break;
            default: break;
            }
        }

        if (rc != GOCA_OK) { c->lError = rc; … return rc; }
        c->uPos += cbOrder;
    }
    return GOCA_OK;
}
```

**Ключевое:** `bInArea`/`uAreaFlags` **не сбрасываются** в начале (N5). Если предыдущий parse оставил `bInArea=TRUE` (без `GEAR`), следующий унаследует. В нормальном GOCA-потоке `GBAR..GEAR` парны, но защита от malformed stream нужна.

## VII.3. `GocaOrderLength`

```c
static inline ULONG GocaOrderLength(GOCA_CTX *c, const BYTE *p, ULONG cbAvail)
{
    UCHAR oc;
    if (cbAvail < 1) return 0;
    oc = p[0];
    if (BYTE_ORDER(oc))  return 1;
    if (oc == OCODE_VLONG) {
        if (cbAvail < 4) return 0;
        return 4u + GocaGetU16(c, p + 2);
    }
    if (SHORT_ORDER(oc)) return 2;
    if (cbAvail < 2) return 0;
    return 2u + (ULONG)p[1];
}
```

**Ключевое:** для `OCODE_GBSEG = 0x70` — `SHORT_ORDER(0x70)` = false, `LONG_ORDER(0x70)` = true. Длина = `2 + p[1] = 2 + 0x0C = 14`. **Корректно.**

## VIII.3. Баг #8 — overflow в poly-*

```c
static inline LONG GocaEmitPolyLine(GOCA_CTX *c, PBYTE buf, ULONG cb,
                                     LONG lCount, PPOINTL aptl)
{
    …
    need = 2 + (ULONG)lCount * 2 * pointSize;
    if (!buf) return (LONG)need;
    if (cb < need) return (LONG)GPI_ALTERROR;
    buf[0] = OCODE_GCLINE;
    buf[1] = (BYTE)(lCount * 2 * pointSize);   // ← overflow, если > 255
    for (i = 0; i < lCount; i++) { … }
}
```

**Проблема:** `buf[1]` — байт. Для LONG (`pointSize=4`): `lCount > 31` → обрезка. Для SHORT (`pointSize=2`): `lCount > 63` → обрезка. `GocaOrderLength` вернёт неверную длину, парсер прочитает середину координат как новый ордер — **порча GOCA-потока**.

**Фикс:** проверять `lCount * 2 * pointSize <= 255`; при превышении — разбивать на несколько ордеров в вызывающей функции (`NGpiPolyLine` — цикл).

# Часть XI. Баги — root cause analysis

## XI.1. Баг #1 — `SrvDeliver` не вставляет в активный сегмент

**Код (dispatch.cpp):**
```c
if (PS_IS_RECORDING(am)) {
    if (!GpiPsGocaAppend(ps, p, cb)) return FALSE;
    …
}
```

`GpiPsGocaAppend` (gpi_ps.h):
```c
memcpy(ps->pbGoca + ps->cbGoca, p, cb);
ps->cbGoca += cb;
```

**Root cause:** `GpiPsGocaAppend` всегда добавляет в конец `pbGoca`. Если открыт существующий сегмент (не последний), ордер попадает **после** всех сегментов, а не в активный.

**Спецификация:** OS/2 PM Ref, `GpiOpenSegment`: «To edit the contents of a segment, … Insert the new primitives by calling any of the Gpi primitive functions.»

**Сценарий:**
```
pbGoca = [GBSEG_1 | body_1 | GBSEG_2 | body_2 | GBSEG_3 | body_3]
GpiOpenSegment(2) → uOpenSegStart = offset(GBSEG_2), lOpenSeg = 2
GpiLine(pt) → SrvDeliver → GpiPsGocaAppend → append в конец:
  pbGoca = [... | body_3 | GCLINE]
GpiCloseSegment
GpiDrawSegment(2) → replay [offset(GBSEG_2), offset(GBSEG_3)) → GCLINE НЕ входит
GpiDrawSegment(3) → replay [offset(GBSEG_3), cbGoca) → GCLINE входит (ошибка)
```

**Фикс:** `ULONG uOpenSegEnd` в `GPI_PS`. В `NGpiOpenSegment` (для существующего сегмента) вычислить один раз. В `SrvDeliver`:
```c
if (PS_IS_RECORDING(am)) {
    if (ps->uOpenSegEnd > 0) {
        if (!SrvGocaInsertBytes(ps, ps->uOpenSegEnd, p, cb)) return FALSE;
        ps->uOpenSegEnd += cb;
    } else {
        if (!GpiPsGocaAppend(ps, p, cb)) return FALSE;
    }
    …
}
```

**Тест:** T151.

## XI.2. Баг #2 — `SEGL` не обновляется

**Код (NGpiOpenSegment):**
```c
GocaPutU16(&ps->goca, gbseg + 8, 0);   /* SEGL */
```

**Код (NGpiCloseSegment):** нет обновления `SEGL`.

**Root cause:** `SEGL` инициализируется нулём и никогда не обновляется. Текущий `GetData`/`GpiPsGocaFindSeg` не использует `SEGL` (вычисляют через `GocaOrderLength`), поэтому баг скрыт.

**Спецификация:** `pmord.h`, `ORDERL_GBSEG.usSegDataLen` — длина тела сегмента.

**Фикс:** в `NGpiCloseSegment` (и `NGpiEndElement` при закрытии последнего элемента):
```c
if (ps->uOpenSegStart > 0 && ps->uOpenSegEnd > ps->uOpenSegStart + 14) {
    USHORT segl = (USHORT)(ps->uOpenSegEnd - ps->uOpenSegStart - 14);
    GocaPutU16(&ps->goca, ps->pbGoca + ps->uOpenSegStart + 8, segl);
}
```

**Тест:** T152.

## XI.3. Баг #3 — GCBOX флаги инвертированы

**Код (goca_emit_prim.h):**
```c
if (lControl & 2) flags |= 0x40;   /* DRO_OUTLINE -> boundary */
if (lControl & 1) flags |= 0x20;   /* DRO_FILL    -> fill     */
```

**Код (goca_parser.cpp, DoBox):**
```c
bBoundary = (fbFlags & 0x40) != 0;
bFill     = (fbFlags & 0x20) != 0;
```

**Root cause:** `pmord.h` определяет `GCBOX_FILL=0x40`, `GCBOX_BOUNDARY=0x20`. Эмиттер и парсер **согласованы друг с другом**, но **оба инвертированы** относительно `pmord.h`. Со stub GRE — не проявляется. С real GRE — ордер интерпретируется неверно.

**Спецификация:** `pmord.h`.

**Фикс:** поменять местами в `goca_emit_prim.h` и `goca_parser.cpp`.

**Тест:** T153.

## XI.4. Баг #4 — `ulStopDraw` не проверяется

**Код (NGpiDrawChain, NGpiDrawFrom, NGpiDrawSegment, NGpiDrawDynamics, NGpiRemoveDynamics):** нет проверки `ps->ulStopDraw`.

**Спецификация:** OS/2 PM Ref, `GpiSetStopDraw`: «SDW_ON: Drawing is suppressed. … PMERR_STOP_DRAW is returned.»

**Фикс:** в начале каждой:
```c
if (ps->ulStopDraw == SDW_ON) return (ULONG)GPI_ERROR;
```

**Тест:** T100, T154.

## XI.5. Баг #5 — `DCTL_DYNAMIC` не проверяется

**Код (NGpiDrawDynamics, NGpiRemoveDynamics):** нет проверки `ps->ulDrawControl & DCTL_BIT(DCTL_DYNAMIC)`.

**Спецификация:** OS/2 PM Ref, `DCTL_DYNAMIC`: «When set to DCTL_OFF, dynamic drawing is suppressed.»

**Фикс:**
```c
if (!(ps->ulDrawControl & DCTL_BIT(DCTL_DYNAMIC))) return 1;
```

**Тест:** T101, T155.

## XI.6. Баг #6 — `GpiPsGet` авто-создаёт PS

**Код (gpi_ps.h):**
```c
static inline PGPI_PS GpiPsGet(HPS hps)
{
    PGPI_PS ps = GpiPsFind(hps);
    if (ps) return ps;
    return GpiPsCreate(hps, 0);   // ← авто-create
}
```

**Root cause:** `GpiPsGet` создаёт PS для неизвестного `hps` (например, `hps=1` из `F_CMD_GET_HPS`, или после `DestroyPS`). `GpiPsCreate((HDC)hps, ...)` → `GocaInit((HDC)hps, ...)` → `c->hdc = (HDC)hps` — фиктивный HDC. Все `Gre*` получат его.

**Спецификация:** OS/2 PM Ref: после `GpiDestroyPS` hps недействителен; `PMERR_INV_HPS`.

**Фикс:**
```c
static inline PGPI_PS GpiPsGet(HPS hps)
{
    return GpiPsFind(hps);   // без auto-create
}
```

Все case-ы должны проверять `if (!ps) return GPI_ERROR;` (большинство уже проверяют).

**Тест:** T14, T156.

## XI.7. Баг #7 — `szlPS` не сохраняется

**Код:** в `GPI_PS` нет поля `szlPS`. `NGpiCreatePS` не сохраняет `a->psizlSize`. `NGpiQueryPS` — stub.

**Спецификация:** `GpiCreatePS(psizlSize)`, `GpiQueryPS(&szl)`.

**Фикс:** `SIZEL szlPS` в `GPI_PS`; `NGpiCreatePS` и `NGpiSetPS` пишут; `NGpiQueryPS` читает (Step K).

**Тест:** T9, T157.

## XI.8. Баг #8 — overflow в poly-*

**Код (goca_emit_prim.h, goca_emit_arc.h):**
```c
buf[1] = (BYTE)(lCount * 2 * pointSize);   // без проверки
```

**Root cause:** для LONG (`pointSize=4`): `lCount > 31` → `buf[1]` обрезается. `GocaOrderLength` вернёт неверную длину, парсер прочитает середину координат как новый ордер — порча GOCA.

**Спецификация:** `pmord.h`: `GCLINE_LMP=31`, `GCLINE_SMP=63`; `GCMRK_LMP=31`, `GCMRK_SMP=63`; `GCBEZ_LMB=10`, `GCBEZ_SMB=21`; `GCFLT_LMP=31`, `GCFLT_SMP=63`.

**Фикс:** проверять `lCount * 2 * pointSize <= 255`; при превышении — разбивать на несколько ордеров в `NGpiPolyLine`/`PolyMarker`/`PolySpline`/`PolyFillet`.

**Тест:** T158.

## XI.9. N4 — `GocaInit((HDC)hps, ...)`

**Код (gpi_ps.h, GpiPsCreate):**
```c
GocaInit(&ps->goca, (HDC)hps, NULL, 0);
```

**Root cause:** HPS используется как HDC. Для серверного `NGpiCreatePS(NULL, ...)` — `hdc = NULL` (безопасно). Для авто-create (`GpiPsGet(1)`) — `hdc = (HDC)1` (фиктивный). Для клиентского `GpiPsCreate((HPS)result, ...)` — `hdc = (HDC)result` (серверный адрес, бессмысленно).

**Спецификация:** архитектура — HDC — линк к Media, не HPS.

**Уточнение после фактчекинга (2026-11-10):** «без HWND на экран не нарисовать» — верно. Но **N4 HWND не требует**:
- **Memory DC** (`DevOpenDC(hab, OD_MEMORY, "*", …)`) даёт HDC без окна. Offscreen-рисование (в `pVBuffmem`) работает без HWND.
- **Screen DC** требует HWND — единственный документированный путь без своего окна: `HWND_DESKTOP` (реальное окно рабочего стола) + `WinOpenWindowDC(HWND_DESKTOP)` или `WinGetScreenPS(HWND_DESKTOP)`.
- `HWND_DESKTOP` — не «псевдо-HWND», а символическое имя (`0x00000001` в `PMWIN.H`) для реального окна рабочего стола, создаваемого PM при старте (IBM PM Ref Vol.1).

**Фикс:** `GpiPsCreate(hps, hdc, flOptions)`; `GocaInit(&ps->goca, hdc, NULL, 0)`. Путь `hdc` по фазам:

| Фаза | `goca.hdc` | Откуда | Что работает |
|---|---|---|---|
| P0 | `NULL` | — | GOCA-поток, сегменты, bookkeeping; `Gre*` — заглушки |
| Step K | HDC от клиента | `NGpiAssociate(hdc)` | То же |
| Phase 4 | memory DC | `DevOpenDC(OD_MEMORY)` | Offscreen в `pVBuffmem`; визуально ничего |
| Phase 6 | screen DC | `WinOpenWindowDC(HWND_DESKTOP)` / `WinGetScreenPS(HWND_DESKTOP)` | **Реальный экран** |

Сервер: `GpiPsCreate(NULL, a->hdc, flOptions)`. Клиент: `GpiPsCreate((HPS)result, NULL, flOptions)`. `NGpiAssociate` устанавливает `goca.hdc` (Step K).

**Тест:** T159, T160 (без HWND), T206–T208 (с HWND — после Phase 6).

## XI.10. N5 — `bInArea`/`uAreaFlags` не сбрасываются

**Код (GocaParseStream):** нет сброса в начале.

**Root cause:** если предыдущий parse оставил `bInArea=TRUE` (malformed stream без `GEAR`), следующий унаследует. В нормальном GOCA-потоке `GBAR..GEAR` парны, но защита нужна.

**Фикс:**
```c

{
    c->uPos = 0;
    c->lError = GOCA_OK;
    c->bInArea = FALSE;
    c->uAreaFlags = 0;
    …
}
```

**Тест:** T161.

## XI.11. Extra — `RefreshCurPos` в `DoLine` для `GCLINE`

**Код (goca_parser.cpp, DoLine):**
```c
if (bCur) {
    …
    RefreshCurPos(c);   // ← GreGetCurrentPosition
    pptl[0] = c->ptlCurPos;
    …
}
```

**Root cause:** для `GCLINE` позиция уже в `c->ptlCurPos` (обновлена предыдущим `GSCP`/`GCLINE`). `RefreshCurPos` — лишний `GreGetCurrentPosition` на каждую линию.

**Спецификация:** GOCA `GCLINE` использует current position, которая уже известна.

**Фикс:** удалить `RefreshCurPos` из `DoLine` для `bCur == TRUE`. Оставить только в `GocaInit` (начальная инициализация).

**Тест:** T162.

## XI.12. N7 — `GPI_PS::m_hHab` не инициализируется

**Код (`Fs_Server::DispatchGpi`, `case NGpiCreatePS`):**
```c
ps = GpiPsCreate(NULL, a->flOptions);
// ps->m_hHab остаётся 0 (из memset в GpiPsCreate)
```

**Root cause:** `GPI_PS::m_hHab` объявлен в структуре, но никогда не записывается. `GpiPsDestroyByHab(iHab)` (вызывается из `Fs_HabList::Destroy`/`DestroyAll`) обегает `g_psTable` в поисках `m_hHab == hHab` — находит только 0, PS не уничтожается. При `NWinTerminate` или grace-teardown все PS, созданные в этом HAB'е, **утекают** (живут до завершения процесса сервера).

**Спецификация:** spec2 §4.3, «`GPI_PS::m_hHab` — ссылка на `Fs_Hab`. Нужна для `GpiPsDestroyByHab` (каскадная очистка)».

**Фикс:** `NGpiCreatePS` должен получить текущий HAB из `pRecvobj` и сохранить его номер:
```c
Fs_Connection *pConn   = m_conns.FindByRecvobj(pRecvobj);
Fs_Thread     *pThread = pConn ? pConn->GetThread() : NULL;
Fs_Hab        *pHab    = pThread ? pThread->GetHab() : NULL;
…
ps = GpiPsCreate(NULL, a->flOptions);
if (ps) ps->m_hHab = pHab ? pHab->GetIHab() : 0;
```

При `NGpiDestroyPS` — `ps->m_hHab = 0` (через `memset` в `GpiPsDestroy`).

**Тест:** новый — `WinInitialize` → `GpiCreatePS` → `WinTerminate` → проверка, что `GpiPsFind(hps)` возвращает NULL.

# Часть XIII. Жизненные циклы

## XIII.1. Сервер (`PMSERVER.EXE`)

**On-demand запуск:**

```
Клиент (PMMERGE) стартует
  → PMC_ServerInit: DosLoadModule(PMTCP), resolve ordinals 1,2,4-8
  → LocalServerRunning(): DosOpenMutexSem(FREEPM_MUTEX_NAME)
       — есть → сервер уже работает
       — нет  → ExecuteFreePMServer() (DosExecPgm "PMSERVER.EXE")
                DosSleep(1000)
  → pfnInitServerConnection()
  → PMC_ClientConnect(): F_CMD_CLIENT_CONNECT → F_CLIENTCONFIG
```

**Presence-маркер:** mutex `FREEPM_MUTEX_NAME`. Создаётся в `pmserver.cpp::main` (`DosCreateMutexSem`), освобождается в `atexit(CleanupServer)`. **Presence = «mutex существует», не «mutex свободен».**

**Завершение:** `MonitorLoop` (в отдельном потоке) → после `m_fEverHadClient && nActive == 0` → `exit(0)` → `atexit` → `DosCloseMutexSem` → следующий клиент запустит `PMSERVER.EXE` заново.

**Сигналы:** `SIGINT`/`SIGTERM` → `CleanupServer` + `exit(1)`. `SIGSEGV`/`SIGFPE`/`SIGABRT` не обрабатываются.

**Идентичность:** сервер — **отдельный процесс**, не встраиваемый модуль. `exit(0)` из monitor thread — часть архитектуры on-demand lifecycle, не дефект.

## XIII.2. Поток клиента (`Fs_Thread` + `Fs_Connection`)

```
CONNECT (recvobj, idClient=0)  → m_procs.Create(&m_conns, recvobj) → новый Fs_Process + Fs_Thread + Fs_Connection
                                → m_conns.FindByRecvobj → pConn->GetThread() → SendClientConfig

CONNECT (recvobj, idClient≠0)  → m_procs.FindByIdClient → pProc->AllocThread(&m_conns, recvobj)
                                → SendClientConfig

DISCONNECT (от PMTCP disc_cb)  → m_conns.FindByRecvobj → pConn->Detach(now)
                                  (pThread не уничтожается, HAB сохраняется)

RECONNECT(idClient, tid)       → m_procs.FindByIdClient → pProc->FindThreadByTid(tid)
                                → pThread->GetConn() должен быть Detached
                                → pConn->Attach(recvobj)

PING                           → pConn->Touch()

EXIT                           → TeardownThread(pThread, "EXIT")
                                  → m_habs.Destroy → pThread->ClearHab
                                  → pProc->FreeThread(pThread)
                                  → если последний поток: m_procs.Destroy + m_habs.DestroyAll

EXPIRED (inactive timeout)     → pConn->IsExpiredInactive(now, ulInactive)
                                → pConn->Detach(now)

EXPIRED (grace timeout)        → pConn->IsExpiredGrace(now, ulGrace)
                                → TeardownThread(pThread, "EXPIRE")
```

**Модель:** `Fs_Connection` — состояние транспорта. `Fs_Thread` — состояние клиентского потока, переживает reconnect. `Fs_Process` — клиентский процесс; уничтожается при уходе последнего потока.

## XIII.3. HAB (`Fs_Hab`)

```
Create(idClient, tid) → Free→Used (iHab = m_ulNextHab++)
  ├── NWinTerminate(iHab) → Destroy(idClient, tid, iHab)
  │     ├── GpiPsDestroyByHab(iHab)   (PS с m_hHab == iHab — N7 не работает)
  │     ├── [Phase 4] destroy Queue, ClassList
  │     └── Shutdown()
  │
  ├── CLIENT_EXIT → DestroyAll(idClient)
  └── grace expiry → DestroyAll(idClient)
```

**Инварианты:**
- `iHab` монотонный, **не переиспользуется**.
- `FindByIHab(0)` = NULL, `Create(0, _, _)` = NULL.
- `DestroyAll(idClient)` очищает все HAB-ы сессии; если `idClient == 0` — no-op.
- Strict-режим (`m_cfg.fStrictHab == TRUE`): `NWinTerminate`/`NWinGetLastError` дополнительно проверяют `data == pThread->GetIHab()`.

## XIII.4. PS (`GPI_PS`)

```
NGpiCreatePS(hab, hdc, szl, flOptions)
  → GpiPsCreate(NULL, flOptions)
  → m_hHab = ???  (N7 — не устанавливается, PS не привязан к HAB)
  → szlPS = szl   (баг #7 — поле отсутствует)

  → goca.hdc = hdc

  (N7: не находит ни одного PS — утечка)
```

## XIII.5. Рендеринг (GPI: DM_DRAW / DM_RETAIN / DM_DRAWANDRETAIN)

**DM_DRAW (нет открытого сегмента):**
`Gpi*` → `GocaEmit*` → `SrvDeliver` → `SrvParseOrder` → `GocaParseStream` → `Gre*`.

**DM_RETAIN (сегмент открыт):**
`Gpi*` → `GocaEmit*` → `SrvDeliver` → `GpiPsGocaAppend` (в `pbGoca`). **GRE не вызывается. Persistent registers `goca.lb/cb/mb/ab` не обновляются.**

**DM_DRAWANDRETAIN:** и append, и parse. Регистры обновляются через parse.

**Unchained open segment** (нет `ATTR_CHAINED` в `ulInitialSegAttrs`) — force DM_RETAIN, даже если клиент выставил DM_DRAW/DM_DRAWANDRETAIN.

**Сегменты:** `NGpiOpenSegment` → GBSEG в `pbGoca` → `uOpenSegStart`; `NGpiCloseSegment` → `lOpenSeg = 0`.

**Элементы:** `NGpiBeginElement` → GBEL; примитивы внутри — append; `NGpiEndElement` → GEEL → re-pack в `SrvGocaInsertElement`.

**Пути:** `lOpenPath`, `bPathDefined` — конечный автомат.

## XIII.6. Keepalive / reconnect / shutdown (клиентская сторона)

**Keepalive:** поток `KeepaliveProc`, `pingSec = max(ulInactive/2, 5)`, `F_CMD_CLIENT_PING(idClient)`. При ошибке — `OnTransportError()`.

**Reconnect:** поток `ReconnectThreadProc`, окно `ulGrace`, интервал `max(ulGrace/3, 1)`, `_InitServerConnection` + `F_CMD_CLIENT_RECONNECT(idClient)` + payload `{tid}`. Если `cfg.idClient == idClient` — resume; иначе — `pfnCloseServerConnection`, retry. После `deadline` — session lost.

**Shutdown:** `PMC_ShutdownCallback` вызывается из PMTCP `DllMain(DETACH)`. `atexit` **не** используется (LIFO DETACH: PMTCP раньше PMCLIENT).

# Часть XVII. Инварианты

**I1.** Каждый `recvobj` имеет не более одной ACTIVE `Fs_Connection`.
**I2.** `idClient` монотонный, уникальный в процессе, никогда не переиспользуется.
**I3.** `iHab` монотонный, уникальный в процессе, никогда не переиспользуется.
**I4.** `Fs_Thread` не владеет HAB/PS/WND/DC; только back-ref через `m_pHab`.
**I5.** `Fs_Hab` не владеет PS/WND/DC; только back-ref через `GPI_PS::m_hHab` (N7 — не инициализируется).
**I6.** `GPI_PS::m_hHab` ссылается на валидный HAB (или 0 при `NGpiCreatePS(NULL, ...)` — N7 валидация pending).
**I7.** Reconnect в пределах `ulGrace` не трогает HAB/PS/WND.
**I8.** `m_iHab`/`idClient` монотонные → orphaned HAB/PS (без `DestroyAll`) не переиспользуются.
**I9.** `F_CMD_CLASS_WIN` маршрутизируется через `HandleWinCall` → `DispatchWin*`. HAB (0x0001–0x000F) — sync 8→4, остальные — async 16.
**I10.** `F_CMD_CLASS_GPI` диспетчеризуется per-function через `DispatchGpi`; `F_CMD_GPI_DISPATCH` отсутствует и не нужен.
**I11.** `GOCA_CTX` — единственное место persistent registers; `GocaEmit*` не обновляет; `GocaParseStream` обновляет.
**I12.** `ulStopDraw == SDW_ON` подавляет drawing (не реализовано — баг #4).
**I13.** `DCTL_DYNAMIC == DCTL_OFF` подавляет dynamic drawing (не реализовано — баг #5).
**I14.** `NWinTerminate`/`NWinGetLastError` в не-strict режиме игнорируют `data`; HAB берётся у `pThread->GetHab()`.

## A. Wire byte layouts

**GPI class (async):**
```
Fc_SesPostCommand(cmd, hps):   8 B
Fc_SesPostData(&cbArgs, 4):    4 B
Fc_SesPostData(args, cbArgs):  cbArgs B
Total: 12 + cbArgs
Response: 16 (FPM_RESP_HEADER) + cbPayload
```

**WIN HAB class (sync, 0x0001–0x000F):**
```
Fc_SesSendCommand(cmd, data):  8 B (cmd + data)
Response:                      4 B (ulResult)
```

**WIN (async, остальные):**
```
Fc_SesPostCommand(cmd, data):  8 B
Fc_SesPostData(&cbArgs, 4):    4 B
Fc_SesPostData(args, cbArgs):  cbArgs B
Total: 12 + cbArgs
Response: 16 + cbPayload
```

**CORE CONNECT / RECONNECT:**
```
Fc_SesPostCommand(cmd, data):  8 B
(CONNECT: без payload, RECONNECT: + {ULONG tid} = 4 B)
Response: 16 B F_CLIENTCONFIG (не FPM_RESP_HEADER)
```

**GORDER class (не реализован, P8):**
```
1-byte:  cmd(4) + hps(4) = 8 B
2-byte:  cmd(4) + hps(4) = 8 B (data packed in cmd[8..15])
long:    cmd(4) + hps(4) + LEN(1) + data(LEN)
vlong:   cmd(4) + hps(4) + qual(1) + LEN16(2) + data(LEN16)
batch:   cmd(4) + hps(4) + cbBatch(4) + GOCA-stream
```

# Резюме

- **Архитектура:** GPI формирует GOCA-субстанцию PS; GRE рендерит через HDC на Media. PS = поток + регистры + bookkeeping + HDC. Сервер — единственный авторитетный владелец состояния; клиент хранит только opaque-хэндлы.
- **Сервер (as-built):** `Fs_Server` с тремя плоскими реестрами — `Fs_ProcessList` (процессы), `Fs_ConnectionList` (соединения), `Fs_HabList` (HAB). `Fs_Process` владеет `Fs_ThreadList`; каждый `Fs_Thread` содержит back-refs на процесс, соединение и HAB.
- **HAB:** 3 метода `Fs_Server::DispatchWinHab` (Initialize/Terminate/GetLastError); sync 8→4 без `cbArgs`. `fStrictHab` в конфиге включает строгую проверку.
- **GPI:** `Fs_Server::DispatchGpi` — метод; per-function команды; 60+ NGpi* реализовано, ~150 stub. `pRecvobj` пока не используется.
- **Конфигурация:** `F_Config` (base) → `F_ClientConfig` / `F_ServerConfig`; `debugOptions` — общее поле; `fStrictHab` — серверное.
- **HWND:** не требуется для PS/GOCA/GPI-ядра (P0–P3). Реальный экран — только через `HWND_DESKTOP` начиная с Phase 6 (P4.5). Memory DC — offscreen без HWND в Phase 4. `HWND_DESKTOP` — символическое имя реального окна рабочего стола, не «псевдо-HWND».
- **Состояние:** ядро NGpi работает (stub GRE), HAB lifecycle — рабочий. Открыты 8 багов P0 + N4, N5, Extra, N7 + 21 архитектурная проблема.
- **План:** P0 (баги, включая N7) → P1–P3 (Step K/M/J) → P4 (Phase 4, memory DC) → **P4.5** (Phase 6, `HWND_DESKTOP` + screen DC) → P5 (real GRE) → P6–P7 → P8 (GORDER).
- **Тесты:** 179 GPI + 10 Micro/Normal + 5 GORDER + 8 HAB + 2 N7 + 4 HWND = **~208 тестов**.
