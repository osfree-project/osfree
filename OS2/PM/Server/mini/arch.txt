# OS/2 Presentation Manager — Full Architecture (AD 17.0)

## 1. Идентификация

| Поле | Значение |
|---|---|
| Архитектура | OS/2 Presentation Manager — Full Architecture (Window Manager, Graphics, IPC) |
| Система | Оконная и графическая подсистема PM + межпрограммное взаимодействие |
| Версия | AD 17.0 |
| Границы | PM API (Win*, Gpi*), клиент-серверный раздел (PMCLIENT.DLL ↔ wire ↔ PMSERVER.EXE / Fs_Server::HandleCommand), GRE (Gre* + Dispatch Table / OS2_PM_DRV_ENABLE + VMI), драйверные модели (Dispatch Table, GRADD, SNAP/Nucleus), подсистема шрифтов (FOCA/IFI), метафайлы (MO:DCA-L), подсистема ввода (System Queue), hardcopy-драйверы и спулер (PMSPL, SPOOLCP, PMPRINT.QPR), hooks, clipboard, DDE, atom tables |

**Структура системы**: PM разделён на два процесса, связанных транспортным уровнем:

| Сторона | Состав | Роль |
|---|---|---|
| Клиент | приложение; PMCLIENT.DLL | маршалинг Win*/Gpi* в команды; транспортный клиент |
| Сервер | PMSERVER.EXE; Fs_Server::HandleCommand; PMWIN, PMGPI, PMGRE; DDI (модели 1/2/3); IFI; .met; hardcopy .DRV; PMDD.SYS / System Queue | приём и диспетчеризация команд; владение handle'ами; рендеринг; работа с оборудованием |
| Транспорт | wire: named pipe / TCP/IP (PMSERVER.EXE <> PMCLIENT.DLL) | передача opcode + data между клиентом и сервером |

**Внешние акторы**: приложение (вызывает API, получает сообщения); удалённый клиент (приложение на другой машине, подключающееся к серверу по сети); WPS — потребитель PM API, вне слоя PM; пользователь через устройства ввода; устройство вывода (дисплей, принтер, плоттер); файловая система (.met, файлы шрифтов, spool file); другое приложение как clipboard/DDE-партнёр.

**Что пересекает границу**:

| Направление | Содержимое |
|---|---|
| вход | Gpi*/Win* от приложения; opcode + data команды от PMCLIENT.DLL через wire (named pipe / TCP/IP); connect / F_CMD_GET_IHAB / F_CMD_CLIENT_RECONNECT → HandleCoreCommand; GPI-команды → HandleGpiCall; PMWIN-команды → HandleWinCall; Win* от WPS; SQMSG от PMDD; Gre* через Dispatch Table (16-бит и 32-бит) или VMI_CMD_* к VMAN (Warp 4); .met при проигрывании (GpiPlayMetaFile); данные clipboard; DDE-сообщения; перехват через hooks; запросы GRE к IFI-драйверу (загрузка шрифта, метрики, глифы); spooler API от hardcopy .DRV |
| выход | WM_* в HMQ приложения; ihab / clientId, результаты, события от сервера к клиенту; команды устройства от display- или hardcopy-драйвера; GOCA orders в .met; растр в memory bitmap; job data в spool file; байты .met на диск; глифы (растровые/контурные) от IFI-драйвера к GRE; данные clipboard; DDE-сообщения |

**Подсистема ввода**: PMDD.SYS (Ring 0) помещает события в системную очередь (System Queue), которая является циклическим массивом структур SQMSG. SQMSG доставляется в PMWIN сервера. Приложение получает сообщения через свою очередь (QMSG), асинхронные (WinPostMsg) и синхронные (WinSendMsg, список SMS). Сообщения между окнами разных клиентов проходят через сервер (HandleWinCall).

**GOCA**: определяет GPS — двумерное концептуальное пространство, не зависящее от среды, в котором определяются drawing orders. В OS/2 PM GPS материализуется как PS (GpiCreatePS); drawing orders существуют только в retained-контексте (segment store, буферы orders, .met).

**Три драйверные модели** (вложенные; хостятся в процессе сервера):

| Модель | Точка подключения | Трансляция | Компоненты |
|---|---|---|---|
| 1. Dispatch Table | DDI → DispatchTable[func_no] | прямая .DRV; 16-бит (1.1–1.3) и 32-бит (2.0+) — одна модель, разная разрядность | .DRV; display .DRV и hardcopy .DRV — обе модели 1 |
| 2. GRADD (через модель 1) | DispatchTable → GRE2VMAN → VMI → VMAN → GHI | GRE2VMAN (GRE→VMI), GHI (VMAN→GRADD) | GRE2VMAN, VMAN, GRADD, SOFTDRAW |
| 3. SNAP/Nucleus (через модель 2) | VMAN → GHI → SNAP-драйвер → Nucleus | SNAP-драйвер транслирует GHI в вызовы Nucleus | SDDGRADD, Nucleus (ядро + BPD) |

**Доступ к устройству**:

| Компонент | Модель | Характер доступа |
|---|---|---|
| .DRV (display) | 1 | прямой |
| hardcopy .DRV | 1 | прямой (через PRTxxx при OD_DIRECT; через SplQm* при OD_QUEUED) |
| SOFTDRAW | 1 (опц.) и 2 (fallback) | библиотека; пишет в aperture, предоставленный вызывающим |
| GRADD | 2 | прямой; только GRADD имеют прямой доступ к видеооборудованию |
| Nucleus (BPD) | 3 | прямой |

SOFTDRAW — единая DLL (SOFTDRAW.DLL), графическая библиотека, экспортирующая SDBitBlt и SDLine; получает указатель на линейный адрес (VRAM bit map или системный bit map) и рисует напрямую в него. Не является путём к устройству.

IFI — прямой вызов PMGRE к драйверам шрифтов; к устройству не идёт.

Гибридный GRE: Dispatch Table в Warp 4 обслуживает обе ветви. Старый DDI-драйвер попадает в модель 1 и не знает о VMAN; GRADD-драйвер загружается через GRE2VMAN в модель 2. 16-битный PM старше гибридного GRE и в гибридность не входит.

**DC и graphic orders**:

| Тип DC | Устройство | Драйвер |
|---|---|---|
| Window DC | дисплей | display (модель 1/2/3) |
| OD_QUEUED / OD_DIRECT | принтер, плоттер | hardcopy .DRV (модель 1), загружается при DevOpenDC |
| OD_METAFILE / OD_METAFILE_NOQUERY | .met | без драйвера устройства; GOCA orders |
| OD_MEMORY | bitmap | без драйвера устройства |
| OD_INFO | принтер, плоттер (только запрос) | hardcopy .DRV; вывод не производится |

**Режимы рисования**:

| GpiSetDrawingMode | Chained | Unchained | Вне сегмента |
|---|---|---|---|
| DM_DRAW | draw; orders не формируются | retain; orders в segment store | draw; orders не формируются |
| DM_RETAIN | retain; orders в segment store | retain; orders в segment store | draw; orders не формируются |
| DM_DRAWANDRETAIN | draw и retain | retain | draw; orders не формируются |

Segment store, элементы и element pointer существуют только в retained-контексте. Element pointer и edit mode (SEGEM_INSERT / SEGEM_REPLACE) действительны только в DM_RETAIN. Micro PS не имеет segment store; режим всегда DM_DRAW. Смена GpiSetDrawingMode в уже созданном PS разрешена вне сегментного bracket; внутри открытого сегмента — ошибка.

| SOFTDRAW | 1 (опц.) и 2 (fallback) | библиотека; пишет в aperture, предоставленный вызывающим |
| GRADD | 2 | прямой; только GRADD имеют прямой доступ к видеооборудованию |
| Nucleus (BPD) | 3 | прямой |

SOFTDRAW — единая DLL (SOFTDRAW.DLL), графическая библиотека, экспортирующая SDBitBlt и SDLine; получает указатель на линейный адрес (VRAM bit map или системный bit map) и рисует напрямую в него. Не является путём к устройству.

IFI — прямой вызов PMGRE к драйверам шрифтов; к устройству не идёт.

Гибридный GRE: Dispatch Table в Warp 4 обслуживает обе ветви. Старый DDI-драйвер попадает в модель 1 и не знает о VMAN; GRADD-драйвер загружается через GRE2VMAN в модель 2. 16-битный PM старше гибридного GRE и в гибридность не входит.

DC и graphic orders:

| Тип DC | Устройство | Драйвер |
|---|---|---|
| Window DC | дисплей | display (модель 1/2/3) |
| OD_QUEUED / OD_DIRECT | принтер, плоттер | hardcopy .DRV (модель 1), загружается при DevOpenDC |
| OD_METAFILE / OD_METAFILE_NOQUERY | .met | без драйвера устройства; GOCA orders |
| OD_MEMORY | bitmap | без драйвера устройства |
| OD_INFO | принтер, плоттер (только запрос) | hardcopy .DRV; вывод не производится |

Режимы рисования:

| GpiSetDrawingMode | Chained | Unchained | Вне сегмента |
|---|---|---|---|
| DM_DRAW | draw; orders не формируются | retain; orders в segment store | draw; orders не формируются |
| DM_RETAIN | retain; orders в segment store | retain; orders в segment store | draw; orders не формируются |
| DM_DRAWANDRETAIN | draw и retain | retain | draw; orders не формируются |

Segment store, элементы и element pointer существуют только в retained-контексте. Element pointer и edit mode (SEGEM_INSERT / SEGEM_REPLACE) действительны только в DM_RETAIN. Micro PS не имеет segment store; режим всегда DM_DRAW. Смена GpiSetDrawingMode в уже созданном PS разрешена вне сегментного bracket; внутри открытого сегмента — ошибка.

| Объект | Защита | Область |
|---|---|---|
| HMQ | mutex (DosRequestMutexSem) | per-thread; Post — из другого потока |
| System Queue | ядро PMDD | global |
| PS | не потокобезопасен; принадлежит создавшему потоку | per-thread |
| DC / Dispatch Table | сериализация на уровне GRE | per-DC |
| VMAN | семафор VMAN — сериализует доступ к GRADD и SNAP | global |
| Кэш шрифтов | внутренняя синхронизация GRE | global |
| Spooler | внутренняя синхронизация спулера | global (очередь) |
| PMSEM / GRESEM | см. V11 | global |
| Fs_ClientList | мьютекс OS/2 (DosRequestMutexSem) | слоты сессий |
| Fs_HabList | мьютекс OS/2 | m_aHabs[], m_ulNextHab |
| Поток-монитор | тик 1000 мс | Active→Detached (inactive 60 c), Detached→Free (grace 30 c) |

Program Inversion: WinGetMsg не возвращает управление в цикл приложения, а вызывает wndproc внутри себя. PM владеет циклом диспетчеризации; hooks и модальные циклы работают до приложения.

Focus: единственное окно на систему получает клавиатурный ввод. При активации система поднимает frame-окна между HWND_DESKTOP и фокусным окном, отправляет WM_ACTIVATE и WM_SETFOCUS.

Capture: WinSetCapture переопределяет маршрут мыши — все события идут в capture-окно независимо от позиции курсора.

VMAN helper-функции: VHAllocMem, VHFreeMem, VHLockMem, VHPhystoVirt, VHMap, VHMapVRAM — GRADD не делает прямых вызовов ОС.

Управление указателем: VMAN полностью отвечает за курсор; VMI_CMD_MOVEPTR уведомляет VMAN; при RC_SIMULATE VMAN использует bitblt для симуляции движения указателя.

### V6 Font Subsystem

FOCA (Font Object Content Architecture) — ресурсная архитектура: структура, метрики, глифы. Определена в PMFONT.H.

GOCA (Graphics Object Content Architecture) — команды отображения символов (text orders) в PS/DC. GOCA также определяет GPS — концептуальное пространство, в котором определяются orders; GPS не зависит от среды; в OS/2 PM материализуется как PS.

IFI (Intelligent Font Interface) — API для поддержки произвольных outline-технологий (TrueType, Type1 и др.). IFI-драйверы — dynalink DLL, вызываемые только GRE.

UGL (Universal Glyph List) — управление глифами для многоязычной поддержки; внутренний каталог глифов.

PMFONT.H — заголовочный файл структур FOCA: FOCAMETRICS, FONTSIGNATURE, FONTDEFINITIONHEADER.

FOCA-структуры и маппинг метрик — см. V3.

Поток отображения текста — см. V3.

FOCA не имеет номеров ордеров в PMORD.H. Это ресурсная архитектура, а не поток команд. GOCA-ордера ссылаются на FOCA-шрифт через логический шрифт PS.

IFI-драйверы в OS/2: TRUETYPE.DLL, FreeType/2-IFI (замена TRUETYPE.DLL). Приложения не взаимодействуют с IFI-драйверами напрямую.

### V7 Window Management

Concern: иерархия окон, frame/client/control, Z-order, активация, перерисовка, классы окон.

Типы окон:

| Тип | Описание |
|---|---|
| Desktop window | базовое окно сеанса PM; рисует фон; основа для всех окон |
| Desktop-object window | невидимая основа для координирующих окон |
| Frame window | application main window; содержит client window и control windows (title bar, System menu) |
| Client window | область приложения внутри frame |
| Control window | дочернее окно frame или dialog (title bar, menu bar, icons) |
| Dialog | временное окно для ввода; управляется dialog manager |
| Message box | предопределённый диалог для уведомлений |
| Menu | pop-up или pulldown; control window класса WC_MENU |

Window class:

| Элемент | Назначение |
|---|---|
| WinRegisterClass | регистрация класса |
| WINDOWCLASS | pfnWindowProc, flClassStyle, cbWndExtra |
| WinSubclassWindow | subclassing существующего класса |
| WinQueryClassInfo | запрос информации о классе |

Иерархия parent-child-owner: control window всегда owned by frame или dialog; frame является parent'ом своих frame-control окон (icons, menu bar) и одновременно их owner. Parent определяет координатную систему и clip; owner получает нотификации.

Z-order и активация: frame-подъём при активации; WM_ACTIVATE / WM_SETFOCUS; frame-окна между HWND_DESKTOP и фокусным окном.

Перерисовка: invalid region; clip по Z-order; WM_PAINT; синхронная перерисовка контролов.

Стейкхолдер: разработчик приложений (иерархия, Z-order, активация).

### V9 Inter-Application Communication

Concern: hooks (input/sent-message/message-filter), clipboard, DDE, atom tables, разделяемая память.

Hooks:

| Hook | Регистрация | Назначение |
|---|---|---|
| Input hook | WinSetHook | перехват ввода до маршрутизации |
| Sent-message hook | WinSetHook | перехват WinSendMsg |
| Message-filter hook | WinSetHook | фильтрация сообщений в цикле |

| Функция | Назначение |
|---|---|

| WinEnumClipbrdFmts | перечисление форматов |

DDE:

| Сообщение | Назначение |
|---|---|
| WM_DDE_INITIATE | broadcast INITIATE всем приложениям |
| WM_DDE_INITIATEACK | ответ на INITIATE |

Стейкхолдер: интегратор (DDE/clipboard между приложениями), разработчик приложений (hooks для расширения поведения).

### V11 Resource Serialization

Concern: сериализация разделяемых ресурсов PM и GRE, блокировки, владение.

PMSEM / GRESEM: композитная структура семафора (signature PMSEM / GRESEM, 386 semaphore byte, owner pid/tid, nested count, event semaphore handle).

Перечень PM-семафоров: PMSEM_ATOM, PMSEM_USER, PMSEM_VISLOCK, PMSEM_HOOK, PMSEM_HEAP, PMSEM_CLIP, PMSEM_INPUT, PMSEM_DESKTOP, PMSEM_TIMER, PMSEM_CONTROLS.

Перечень GRE-семафоров: GRESEM_Init, GRESEM_PDEV, GRESEM_HFont, GRESEM_FntDrvr, GRESEM_GlobalData, GRESEM_DriverSem, GRESEM_semIfiCache.

Механизм: PMRequestMutexSem; polling на встроенном event semaphore с ограниченным временем; поток может выглядеть blocked/ready/running в зависимости от цикла polling.

Серверные семафоры:

| Объект | Защита | Область |
|---|---|---|
| Fs_ClientList | мьютекс OS/2 | список сессий |
| Fs_HabList | мьютекс OS/2 | таблица HAB |
| Grace/inactive | монитор | глобально на сервере |

Это не PMSEM/GRESEM — другой уровень и другой набор объектов.

Стейкхолдер: интегратор, разработчик драйверов (кто с кем конкурирует за PMSEM_CLIP, PMSEM_HOOK, GRESEM_FntDrvr).

### V12 Printing / Non-display DC

Concern: device independence для всех типов DC; hardcopy-драйверы (модель 1); спулер и queue processor; replay .met в не-дисплейный DC; ограничения прямого вывода.

Типы DC и путь после PMGPI/PMGRE:

| DC type | Устройство | Драйвер / путь | Spooler |
|---|---|---|---|
| Window DC | дисплей | display DDI (модель 1/2/3): .DRV / GRADD / SNAP | нет |
| OD_QUEUED + PM_Q_STD | принтер, плоттер | hardcopy .DRV → PMSPL.DLL → spool file → queue processor (PMPRINT.QPR) → kernel driver | да |
| OD_QUEUED + PM_Q_RAW | принтер, плоттер | hardcopy .DRV → PMSPL.DLL → spool file (raw) → queue processor | да |
| OD_DIRECT | принтер, плоттер | hardcopy .DRV → PRTxxx → kernel driver (spooler обойдён) | нет |
| OD_INFO | принтер, плоттер | hardcopy .DRV; вывод не производится; только запрос caps/properties | нет |
| OD_METAFILE / OD_METAFILE_NOQUERY | .met | без драйвера устройства; GOCA orders → MO:DCA-L | нет |
| OD_MEMORY | bitmap | без драйвера устройства; растр в память | нет |

Модель hardcopy .DRV: hardcopy .DRV — presentation driver модели 1. Загружается при DevOpenDC(OD_QUEUED / OD_DIRECT / OD_INFO). Транслирует стандартный device-independent поток GPI в device-dependent raw data (управляющие коды принтера). Для OD_DIRECT использует PRTxxx-вызовы; для OD_QUEUED — spooler API (SplQmOpen, SplQmStartDoc, SplQmWrite, SplQmEndDoc, SplQmClose). OD_INFO не создаёт job и не пишет данных; служит для GreQueryHardcopyCaps и запроса свойств.

Spooler: PMSPL.DLL — API спулера: очереди, задания, принтеры, драйверы. SPOOLCP.DLL — helper code-page support (DosPFSActivate, DosPFSQueryAct, DosPFSVerifyFont, DosPFSCloseUser). PMPRINT.QPR — штатный queue processor PM; обязанные типы данных — PM_Q_STD и PM_Q_RAW. Спулер хранит job на диске (spool file), управляет очередью (FIFO / priority), асинхронно передаёт queue processor'у. Print Manager — UI спулера (WPS printer object). При отключённом спулере OD_QUEUED деградирует до поведения OD_DIRECT.

Device independence: что сохраняется и что нет:

· Gpi* не привязаны к дисплею. Один и тот же код работает на window / printer / memory / .met DC; целевое устройство определяется DevOpenDC.
· Retained mode и .met — device-independent контейнеры; GpiPlayMetaFile проигрывает orders в любой целевой DC.
· Ограничения: bitmap-операции на принтере зависят от hardcopy .DRV; корреляция (GpiCorrelate*) только в retained; OD_INFO не допускает вывода; OD_METAFILE_NOQUERY запрещает запрос атрибутов.
· Масштабирование: OD_DIRECT по умолчанию печатает «actual size»; OD_QUEUED — «scaled to fit» (различие поведения, не API).

Lifecycle:

| Артефакт | Создание | Уничтожение |
|---|---|---|
| hardcopy DC | DevOpenDC(OD_QUEUED / OD_DIRECT / OD_INFO) | DevCloseDC |
| spool file | SplQmOpen / DevOpenDC(OD_QUEUED) | SplQmClose; queue processor удаляет после печати |
| print job | SplQmStartDoc / DEVESC_STARTDOC | SplQmEndDoc / DEVESC_ENDDOC; job ID возвращается спулером |
| .met | DevOpenDC(OD_METAFILE) | GpiDeleteMetaFile / DevCloseDC |

Стейкхолдеры: разработчик приложений (device independence, replay .met в принтер, выбор OD_QUEUED vs OD_DIRECT); разработчик hardcopy .DRV (DDI модели 1, PRTxxx, spooler API, GreQueryHardcopyCaps); интегратор (спулер, queue processor, Print Manager / WPS printer object, PMSPL / SPOOLCP).

### V13 Client/Server Boundary

Concern: где проходит граница между клиентом и сервером; что пересекает границу; что остаётся на каждой стороне; владение handle'ами; маршрутизация сообщений; синхронизация; развёртывание.

Граница: транспортный уровень (Fs_PfnSend / Fs_PfnRecv), реализованный через named pipe или TCP/IP. Всё выше — клиент; всё ниже — сервер.

Что пересекает границу:

| Что | Направление | Точка в коде |
|---|---|---|
| opcode + data команды | клиент → сервер | PMCLIENT.DLL → Fs_PfnSend |
| connect / F_CMD_GET_IHAB / F_CMD_CLIENT_RECONNECT | клиент → сервер | HandleCoreCommand |
| GPI-команды | клиент → сервер | HandleGpiCall |
| PMWIN-команды | клиент → сервер | HandleWinCall |
| ihab / clientId | сервер → клиент | Fs_HabList |
| результаты, события | сервер → клиент | Fs_PfnSend |

Что остаётся на клиенте: приложение; Win*/Gpi* (API-контракт); PMCLIENT.DLL (маршалинг); очередь сообщений процесса.

Что остаётся на сервере: Fs_Server::HandleCommand; PMWIN; PMGPI; PMGRE; Fs_ClientList; Fs_HabList; поток-монитор; DDI (модели 1/2/3); IFI; .met; hardcopy-ветвь; PMDD.SYS / System Queue.

Владение handle'ами:

| Handle | Владелец | Форма |
|---|---|---|
| HAB | Сервер (Fs_HabList) | индекс в m_aHabs[] |
| HWND | Сервер | индекс в серверном массиве WND |
| DC | Сервер | индекс в F_DC |
| HPS | Сервер | индекс в F_PS |
| HMQ | Поток | очередь в процессе; межпроцессные сообщения идут через сервер |

Маршрутизация сообщений:

| Источник → получатель | Путь |
|---|---|
| тот же поток | напрямую |
| другой поток того же клиента | косвенно, без очереди |
| другой клиент | через сервер (HandleWinCall) |

Синхронизация:

| Объект | Защита | Область |
|---|---|---|
| Fs_ClientList | мьютекс OS/2 | список сессий |
| Fs_HabList | мьютекс OS/2 | таблица HAB |
| Grace/inactive | монитор | глобально на сервере |

Развёртывание:

| Компонент | Ring | Форма |
|---|---|---|
| PMSERVER.EXE | 3 | EXE |
| PMCLIENT.DLL | 3 | DLL |
| wire | — | named pipe / TCP/IP |
| PMWINDOW.DLL / PMDRIVER.DLL | 3 | DLL |

| Период | Модель | Ключевое изменение |

| OS/2 Warp 3 | SOFTDRAW (метадрайвер) | Графический движок теперь поддерживает SOFTDRAW, программный растеризатор; драйверы могут делегировать рисование в память и на экран SOFTDRAW |
| OS/2 Warp 4 | GRADD (VMAN + GRADD) | GRE2VMAN загружается как DDI-драйвер; VMAN; RC_SIMULATE; SOFTDRAW через VMAN; модель 1 сохраняется |

| ArcaOS | SNAP как GRADD | SNAP лицензирован Arca Noae; продолжение линии |
| 2026 | Клиент-серверная | PMCLIENT.DLL ↔ wire ↔ Fs_Server; DDI/GRADD/SNAP хостятся в сервере; hardcopy сохраняется |

Hardcopy-драйверы и спулер существуют во всех версиях линии (1.1 → ArcaOS) как модель 1; от версии к версии меняются spooler API и queue processor, но не точка подключения (DevOpenDC → Dispatch Table).

## 6. Rationale

| Решение | Причина |
|---|---|
| Модель 2 через модель 1 | GRE2VMAN загружается как DDI-драйвер и перехватывает Gre* в Dispatch Table |
| Модель 3 через модель 2 | SNAP-драйвер получает GHI от VMAN и транслирует в вызовы Nucleus |
| SOFTDRAW — единая DLL | Не путь к устройству; активируется вызывающим; aperture предоставляется .DRV или GRADD через VMAN |
| RC_SIMULATE → GHI_CMD_REQUESTHW → SOFTDRAW | Единый механизм программной эмуляции в модели GRADD |
| IFI — прямой вызов GRE | Только GRE вызывает IFI-драйверы; приложения не зависят от шрифтовой технологии |
| MO:DCA-L для .met | GOCA (вектор) + IOCA (растр), совместимость с AFP |
| Гибридный GRE | Совместимость старых DDI-драйверов при появлении GRADD |
| V6 Font Subsystem | Concerns разработчика шрифтов не покрываются V1–V5 полностью |
| 16-бит PM как отправная точка | OS/2 1.1–1.3 — первая реализация PM; 32-битный GRE появился в 2.0 fixpack |
| SNAP в линии Warp 4.5 → eCS → ArcaOS | SNAP вошёл в дистрибутив с Warp 4.5; унаследован eCS и ArcaOS; лицензирован Arca Noae |
| V7 Window Management | Concerns разработчика приложений в части иерархии окон, Z-order, активации не покрывались V1–V6 |
| V8 Controls / Dialogs / Menus | Concerns CUA-совместимости, диалогов, элементов управления не покрывались V1–V6 |
| V9 Inter-Application Communication | Concerns hooks, clipboard, DDE, atom tables не покрывались V1–V6 |
| V11 Resource Serialization | V4 фрагментарен (HMQ/DC/VMAN); полная карта PMSEM/GRESEM — самостоятельный concern интегратора |
| V12 Printing / Non-display DC | Печать и не-дисплейные DC — самостоятельный concern: hardcopy-драйверы модели 1, спулер, queue processor, replay .met; не покрываются V1–V9 и не сводятся к дисплейному пути |
| WPS вне слоя PM | WPS — потребитель PM API, не часть PM; concerns WPS-разработчика (SOM/IDL) не относятся к PM |
| Клиент-серверная граница по транспортному уровню | Позволяет удалённые клиенты и кроссплатформенный транспорт, не меняя Win*/Gpi* для приложения |
| Диспетчеризация через HandleCommand | Единая точка маршрутизации GPI/PMWIN/core, изолирует протокол от реализации |
| Централизованное владение HAB/сессиями | Устраняет локальные таблицы процессов, даёт единый учёт и таймауты |
| Сохранение hardcopy-ветви в сервере | Печать не зависит от дисплейной модели; модель 1 остаётся нужной |
