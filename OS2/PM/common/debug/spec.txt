# Часть I. Спецификация

## 1. Архитектура

**Единственная реализация — PMDEBUG.DLL.** Все остальные бинари (PMSERVER.EXE, PMCLIENT.DLL, PMTCP.DLL, PMGPI) линкуются с ней и вызывают `F_DbgPrint` / `F_DbgCtxEnterf` / `F_DbgCtxExitf` / `F_DbgFatal`.

```
PMSERVER.EXE ─┐
PMCLIENT.DLL ─┼──► PMDEBUG.DLL ──► файл / stderr / syslog / wire
PMTCP.DLL ────┤
PMGPI ────────┘
```

`F_DbgInit` вызывается **из DllMain(ATTACH) самой PMDEBUG.DLL** с дефолтной конфигурацией (из кода). К моменту, когда PMDEBUG вернула управление загрузчику, mutex создан, TLS-слот для контекстного стека выделен, `s_cfg` содержит дефолты, `F_DbgLevels[]` распарсены из `F_DBG_DEFAULT_LEVELS`. Модули, загружающиеся **после** PMDEBUG (а все остальные загружаются после, так как PMDEBUG — их зависимость), сразу имеют работающий `F_DbgPrint`.

**Файл лога DllMain не открывает.** `F_DbgInit` не касается файловой системы. Лог открывается **лениво, при первой записи** (см. §11.4). Следствие: загрузка `pmserver.exe` или любого клиентского процесса не создаёт `freepm.log` — файл появляется только если процесс реально что-то пишет в лог, и с тем именем, которое к моменту первой записи стоит в `s_cfg.logfile`.

Загружающий процесс может переопределить конфигурацию через `F_DbgInit` (второй раз, из `main()`) или `F_DbgSetConfig` (из любого места после чтения `.ini`). После переопределения следующий write открывает файл по новому пути; ранее открытый файл закрывается.

## 2. Модель сообщения

| Ось | Значения | Где задаётся |
|---|---|---|
| `section` | `F_DBG_SEC_*` из `F_config.h` | На месте вызова |
| `level` | 0..10 | На месте вызова |
| `kind` | `PRINT`/`WARNING`/`IGNORING`/`FATAL` | На месте вызова |
| `ctx` | 0..`F_DBG_CTX_MAX` | `F_DbgCtxEnterf` / `Exitf`, per-thread |

**Фильтр:** `level <= F_DbgLevels[section]`. `F_DbgLevels[section] == -1` — отбрасывается всё. `section` вне `[0, 64)` — отбрасывается.

**Единый порог `thresholdLevel`** определяет, идёт ли сообщение в каналы. Если `level > thresholdLevel` — не идёт ни в файл, ни в stderr, ни в syslog, ни в wire. `F_DbgLevels[section]` фильтрует раньше — до порога.

## 3. API

```c
struct F_DbgConfig {
    const char *logfile;
    int         rotateNumber;
    int         rotateSize;
    int         buffered;
    int         ansiColor;
    int         beepOnFatal;
    int         useSyslog;
    int         thresholdLevel;   /* единый порог для всех каналов */
};

/* Инициализация. Создаёт mutex и TLS-слот (один раз за процесс),
   копирует cfg, сбрасывает уровни, парсит levels.
   НЕ открывает лог-файл. Повторный вызов безопасен: переопределяет
   s_cfg, закрывает ранее открытый файл (если был), сбрасывает
   "лог-уже-открывали" — следующая запись откроет по новому пути. */
void APIENTRY F_DbgInit(const F_DbgConfig *cfg, const char *levels);

/* Переопределение конфигурации на лету (после ini).
   Закрывает ранее открытый файл, НЕ открывает новый.
   Следующая запись откроет по s_cfg.logfile. Wire sink не трогает. */
void APIENTRY F_DbgSetConfig(const F_DbgConfig *cfg);

void APIENTRY F_DbgSetLevels(const char *levels);

/* Принудительная ротация. No-op, если файл ещё не открывался
   (нечего ротировать) или rotateNumber <= 0. */
void APIENTRY F_DbgRotate(void);

/* Сброс буферов. No-op, если файл не открыт (нечего сбрасывать);
   stderr всё равно flushes. */
void APIENTRY F_DbgFlush(void);

void APIENTRY F_DbgPrint(int section, int level, const char *fmt, ...);
void APIENTRY F_DbgPrintKind(int section, int level, F_DbgKind kind,
                             const char *fmt, ...);

int  APIENTRY F_DbgCtxEnterf(int section, int level, const char *fmt, ...);
void APIENTRY F_DbgCtxExitf(int ctx, const char *fmt, ...);
int  APIENTRY F_DbgCtxEnter(const char *descr);
void APIENTRY F_DbgCtxExit(int ctx);

void APIENTRY F_DbgFatal(const char *msg);
void APIENTRY F_DbgFatalf(const char *fmt, ...);
void APIENTRY F_DbgAssert(const char *msg, const char *file, int line);
void APIENTRY F_DbgSetShuttingDown(int flag);

typedef void (F_DBG_WIRE_CALLBACK *F_DbgWireSink)(
    F_DbgKind kind, int section, int level, const char *msg);
void APIENTRY F_DbgSetWireSink(F_DbgWireSink sink);
```

## 4. Формат (все строки одинаковые)

| Тип | Формат |
|---|---|
| Обычное | `<counter> <YYYY/MM/DD HH:MM:SS>\|<msg>\n` |
| FATAL | `<counter> <YYYY/MM/DD HH:MM:SS>\|FATAL: <msg>\n` |
| ctx enter | `<counter> <YYYY/MM/DD HH:MM:SS>\|ctx: enter level <N>: '<descr>'\n` |
| ctx exit | `<counter> <YYYY/MM/DD HH:MM:SS>\|ctx: exit  level <N>: '<descr> -> <result>'\n` |

## 5. Контекст

- **Per-thread.** `DosAllocThreadLocalMemory` (см. §7).
- Стек: `char s_ctxDescr[F_DBG_CTX_MAX][F_DBG_CTX_MAX_LEN]` в TLS-памяти.
- `F_DBG_CTX_MAX = 32`, `F_DBG_CTX_MAX_LEN = 256`.
- **Eager с фильтром.** `Enterf`/`Exitf` печатают сразу, если `level <= threshold`. Иначе — `-1` / no-op.
- `F_DbgFatal` **печатает ctx-prelude** (весь активный стек), затем `FATAL:`.
- `F_CMD_CTX_OPEN` от клиента → `F_DbgCtxEnterf` в потоке клиента. `F_CMD_CTX_CLOSE` → `F_DbgCtxExit(-1)`.
- `Fs_Server::HandleDisconnect` → `F_DbgCtxExit(-1)`.

## 6. Wire

| Команда | Opcode | Payload |
|---|---|---|
| `F_CMD_DB_PRINT` | `0x0064` | `struct FDBG_WIRE { int section; int level; int kind; int cbText; char text[cbText]; }` |
| `F_CMD_FATAL_COMMON` | `0x0065` | то же, kind=FATAL |
| `F_CMD_CTX_OPEN` | `0x0066` | `struct FDBG_CTX_OPEN { int section; int level; int cbDescr; char descr[cbDescr]; }` |
| `F_CMD_CTX_CLOSE` | `0x0067` | пусто |

**`section` и `level` от клиента передаются на сервер.** Сервер пишет клиентское сообщение под клиентской секцией и с клиентским `level`, что позволяет клиенту управлять детализацией через `fpm.ini` и видеть это в `server.log`.

`F_DbgKind` расширяется: `F_DBG_KIND_CTX_OPEN`, `F_DBG_KIND_CTX_CLOSE`. Wire sink вызывается для ctx-строк тоже — клиентский wire sink их отправляет как `F_CMD_CTX_OPEN/CLOSE`.

## 7. TLS (per-thread)

- **OS/2:** `DosAllocThreadLocalMemory(1, &s_ctxTls)`; `s_ctxTls[0]` — процесс-инвариантный указатель, ядро резолвит в per-thread память.
- **Win32:** `TlsAlloc()` в `s_ctxTls`; доступ через `TlsGetValue` / `TlsSetValue`.
- Стек `DBG_CTX_STACK` выделяется лениво, при первом `F_DbgCtxEnterf` в потоке (`CtxGetOrCreate`).
- Освобождается только при завершении процесса; утечка ограничена числом потоков × ~8 KiB.

## 9. FATAL

- Guard `s_fatalInProgress`.
- **Печатает ctx-prelude** (`ctx: enter level 0..N`), затем `FATAL:`.
- Файл, stderr (при `thresholdLevel > 0`), syslog (`LOG_ALERT`), wire sink (`kind=FATAL`).
- `beepOnFatal` → `DosBeep`.
- `fflush`.
- `abort()`.

`F_DbgAssert` при `s_shuttingDown` возвращает управление, иначе — `F_DbgFatal("assertion failed: ...")`.

## 10. Thread-safety

Один mutex в `F_debug.cpp` (per-process, так как PMDEBUG.DLL загружена один раз в процесс). Под mutex — `s_counter`, `s_log`, `s_logBytes`, `s_logOpenAttempted`, `s_cfg`, `s_inited`, `F_DbgLevels[]` (запись), `s_wireSink`, `s_fatalInProgress`. TLS-стек ctx — без mutex; печать под mutex.

## 11. Конфигурация

### 11.1. Дефолты

```c
static const F_DbgConfig F_DBG_DEFAULT_CFG = {
    "freepm.log", 10, 0, 0, 1, 0, 1, 5
};
```

`F_DbgInit(&F_DBG_DEFAULT_CFG, F_DBG_DEFAULT_LEVELS)` в `DllMain(ATTACH)` PMDEBUG.DLL. **Файл `freepm.log` при этом не создаётся** — `F_DbgInit` только запоминает конфиг (см. §11.4).

### 11.2. Переопределение

Загружающий процесс после чтения своего `.ini`:

```c
/* Вариант A — через F_DbgInit (типичный путь для pmserver.exe):
   переопределить и файл, и уровни одновременно. */
F_DbgInit(&serverCfg, fpmdebug_debugOptions);

/* Вариант B — через F_DbgSetConfig (без сброса уровней): */
F_DbgConfig cfg = F_DBG_DEFAULT_CFG;   /* копия дефолтов */
/* заполняем из ini... */
F_DbgSetConfig(&cfg);
F_DbgSetLevels(fpmdebug_debugOptions);
```

В обоих случаях:

- `F_DbgInit` и `F_DbgSetConfig` **не открывают** лог-файл.
- Если предыдущая инициализация (из `DllMain`) уже успела открыть файл через первый write — он закрывается.
- Следующий write открывает файл по новому `s_cfg.logfile`.

**Следствие для `pmserver.exe`:** `DllMain` PMDEBUG помнит `freepm.log` как имя, но файла нет. `main()` вызывает `F_DbgInit(&F_DBG_SERVER_CFG, ...)` — конфиг меняется на `pmserver.log`. Первая запись `F_DbgPrint("PMSERVER: starting")` создаёт `pmserver.log`. `freepm.log` **не создаётся никогда** этим процессом.

### 11.3. `fpmsrv.ini` / `fpm.ini`

```ini
fpmdebug.logfile=fpmsrv.log
fpmdebug.rotateNumber=10
fpmdebug.rotateSize=0
fpmdebug.buffered=0
fpmdebug.ansiColor=1
fpmdebug.beepOnFatal=0
fpmdebug.useSyslog=1
fpmdebug.thresholdLevel=5
fpmdebug.debugOptions=ALL,7 5,3 7,5 8,0 40,3
```

Ключи, отсутствующие в ini, берутся из дефолтов. `debugOptions` уже читается `Fc_config.cpp` (клиент) и `Fs_config.cpp` (сервер).

### 11.4. Lazy open (deferred open)

**`F_DbgInit` не открывает лог-файл. `F_DbgSetConfig` не открывает. Открытие происходит при первой записи.**

Механизм:

- Флаг `s_logOpenAttempted` (static, per-process). Сбрасывается в `0` в `F_DbgInit` и `F_DbgSetConfig`.
- `EmitFile` (внутренний путь записи в файл) проверяет флаг:
  - если `0` → вызывает `DbgOpenLog()` (открывает `s_cfg.logfile` в режиме `"a+"`, читает `ftell` для `s_logBytes`), ставит флаг в `1`;
  - если `s_log == NULL` после попытки — все дальнейшие write в файл no-op до следующего `F_DbgInit`/`F_DbgSetConfig` (retry — только через эти два вызова).
- `DbgOpenLog` перед открытием закрывает ранее открытый `s_log` (если был), сбрасывает `s_logBytes = 0`.

**Гарантии:**

- `DllMain(ATTACH)` PMDEBUG никогда не создаёт файлов в файловой системе.
- Загрузка `pmserver.exe` без единой `F_DbgPrint` не создаёт `freepm.log`.
- Загрузка клиентского процесса без единой `F_DbgPrint` не создаёт `freepm.log`.
- Если `fpm.ini` указывает `logfile=clients.log`, файл `clients.log` — единственный, что появится; `freepm.log` не создаётся.
- Пока процесс не писал в лог, `F_DbgRotate` и `F_DbgFlush` — no-op относительно файла (stderr всё равно flushes для `F_DbgFlush`).

**Проверка отсутствия двойного handle при реинициализации:** если `DllMain` открыл `freepm.log` через первый write (т.е. кто-то успел написать до `main`), а затем `main()` вызвал `F_DbgInit(&serverCfg, ...)`, `DbgOpenLog` при следующем write закроет `freepm.log` и откроет `pmserver.log`. Двух одновременно открытых handle на разные файлы не бывает.

# Часть II. План миграции

### 3.2. pmserver — приём без логирования

В `Fs_Server::HandleCommand`:

```c
case F_CMD_DB_PRINT: {
    FDBG_WIRE hdr;
    char text[F_DBG_BUFSIZE];
    if (m_pfnRecv(recvobj, &hdr, &len, sizeof(hdr)) != 0) break;
    if (hdr.cbText <= 0 || hdr.cbText >= (int)sizeof(text)) break;
    m_pfnRecv(recvobj, text, &len, hdr.cbText);
    /* Пока только ACK. Запись в F_Debug — следующий этап. */
    SendHeader(recvobj, 0, 1, 0, 0);
    break;
}
case F_CMD_FATAL_COMMON: /* аналогично, ACK */ ...
case F_CMD_CTX_OPEN:     /* принять, ACK */ ...
case F_CMD_CTX_CLOSE:    /* ACK */ ...
```

**Acceptance:** клиент шлёт `[PMGPI]` строки → pmserver отвечает ACK → клиент не блокируется.

F_DbgPrintKind(hdr.section, hdr.level, (F_DbgKind)hdr.kind,
