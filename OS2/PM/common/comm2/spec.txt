# ТЗ: FreePM транспортный слой (`F_Link`, 3 backend) + PMCLIENT per-thread

Версия: актуальна на текущее состояние кода. Транспортный слой (pmtcp, pmpipe, pmshm) собран на OS/2 и Win32, тесты проходят. PMCLIENT реализован под per-thread модель.

---

## Часть I. Архитектурные принципы

### I.1. Слои и граница клиент/сервер

```
Application (клиент)               Application (сервер: реализация PM)
   │                                   │
   ▼                                   ▼
── L6 Wire ─────────────────────────────────────────────
PMGPI/PMMERGE (marshaling)      Fs_Server::HandleGpiCall/WinCall
   │                            + SendHeader (decode/encode)
   ▼                               ▲
── L5 Session ───────────────────────────────────────────
PMCLIENT                         Fs_Server (routing)
  Fc_Ses* (per-thread),          Fs_Process / Fs_Thread / Fs_Hab
  aConns[tid], keepalive,          MonitorLoop (grace expiry)
  reconnect
   │                               ▲
   ▼                               │
── L4 Transport ─────────────────────────────────────────
Fc_Trn* (shared + backend)      Fs_Trn* (shared + backend)
   │                               ▲
   └──── F_Link ─┬─ TcpLink         │
                 ├─ PipeLink        │
                 └─ ShmLink ────────┘
                 (one backend per DLL)
```

**Граница клиент/сервер** проходит по L4/L3 (транспорт). L4–L6 симметричны. L7 асимметричен: клиент — внешнее приложение, сервер — реализация PM.

**L4** — абстрактный транспорт. Публичный API (`Fc_Trn*`/`Fs_Trn*`, 11 функций) одинаков для всех транспортов. Конкретный транспорт (`TcpLink`, `PipeLink`, `ShmLink`) спрятан за `F_Link`, выбирается загрузкой соответствующего backend-DLL.

**GOCA** — L7-внутренний формат сервера, не сетевой слой. На wire не уходит.

### I.2. Per-thread модель

| Сущность | Где | Ключ | Владелец |
|---|---|---|---|
| Транспортное соединение | backend DLL | `obj` (opaque) | backend (`F_Link` instance) |
| Клиентский поток | PMCLIENT | `tid` (OS/2 thread id) | `aConns[tid]` в PMCLIENT |
| Серверный поток | сервер | `pClient` (= `obj`) | backend `Fs_ClientThreadProc` |
| Сессия сервера | сервер | `idClient` (монотонный) | `Fs_Process` |
| HAB | сервер | `iHab` (монотонный) | `Fs_Hab` |
| Клиентский TID в сессии | сервер | `(idClient, tid)` | `Fs_Thread` |

**Один клиентский поток ↔ одно транспортное соединение ↔ один серверный `Fs_ClientThreadProc` ↔ один `Fs_Thread`.**

**`obj` не выходит за пределы PMCLIENT.** PMMERGE (WinInitialize/WinTerminate) не знает про `obj`; `obj` живёт в `aConns[tid].obj` внутри PMCLIENT.

**HAB-таблица в PMMERGE не ведётся.** `WinInitialize` возвращает HAB приложению; приложение само его носит и передаёт в последующие `Win*`-вызовы.

**`F_CLIENTCONFIG` (включая `idClient`) — process-wide**, хранится в PMCLIENT под `g_hmtxState`, заполняется один раз из первого успешного `F_CMD_CLIENT_CONNECT` reply. Последующие connect'ы (новые потоки) проверяют, что сервер вернул тот же `idClient`; остальные поля игнорируются.

**Два `Fc_SesConnect` для одного `tid` невозможны.** Второй вызов (равно как и вызов при слоте `SLOT_BROKEN`) возвращает `(APIRET)-1` без обращения к транспорту. Восстановление после обрыва — исключительно per-slot reconnect thread, запущенный `OnTransportError`.

### I.3. Что убрано

| Убрано | Почему |
|---|---|
| `DllMain` / `_DLL_InitTerm` в PMCLIENT | Backend грузится лениво на первом `Fc_SesConnect` |
| `DllMain` / `_DLL_InitTerm` в backend | WSA в DETACH уже может быть выгружен |
| `pF_pipe` / `g_shutdownCb` в backend | PMCLIENT — единственный держатель `obj` |
| `Fs_Session` / `Fs_SessionList` | Сессия — агрегат (`idClient`), а не сущность |
| `pmque` / `QueueLink` | Заменён на `pmshm`/`ShmLink` |
| `PMC_ShutdownCallback` | Backend его больше не вызывает; `F_CMD_CLIENT_EXIT` шлёт `Fc_SesDisconnect` |
| `Pmc*` API | Переименовано в `Fc_Ses*` (все 5) |
| `Fc_SesBeginThread` / `Fc_SesEndThread` | Заменены на `Fc_SesConnect` / `Fc_SesDisconnect` |
| HAB-таблица в PMMERGE | Не ведётся |
| `Fc_SesInit` / `Fc_SesTerm` | Отсутствуют; backend грузится лениво |

## Часть III. L4 Transport — `F_Link` + 3 backend

### III.1. Схема

```
┌────────────────────────────────────────────────────────────┐
│                  Публичный API (11 exports)                │
│   shared/Fc_trn.cpp (7)        shared/Fs_trn.cpp (2)       │
│   backend (Fc_TrnConnect, Fs_TrnRunListener)               │
└─────────────────────────┬──────────────────────────────────┘
                          │ ((F_Link *)obj)->Send/Recv/...
                          ▼
┌────────────────────────────────────────────────────────────┐
│                F_Link abstract interface                   │
│  Open / Accept / Handshake / Send / Recv / Close           │
└─────────────────────────┬──────────────────────────────────┘
                          │
        ┌─────────┬───────┴───────┐
        ▼         ▼               ▼
    TcpLink   PipeLink        ShmLink
    (pmtcp)   (pmpipe)        (pmshm)
```

### III.2. Публичный API

#### Клиентский (`Fc_Trn*`)

| Функция | Где | Семантика |
|---|---|---|
| `Fc_TrnConnect(char *host, ULONG *obj)` | backend | Создать соединение + handshake. `*obj = 0` при ошибке. |
| `Fc_TrnDisconnect(void *obj)` | shared | Закрыть. `NULL` → no-op. |
| `Fc_TrnPostCommand(void *obj, int cmd, int par)` | shared | Async write 8B. |
| `Fc_TrnPostData(void *obj, void *buf, int len)` | shared | Async write N байт. |
| `Fc_TrnGetData(void *obj, void *buf, int *len, int size)` | shared | Blocking read ровно `size` байт. |
| `Fc_TrnSendCommand(void *obj, int cmd, int par)` | shared | `PostCommand` + `GetData(4)`. Возврат — `retcode` или `-1`. |
| `Fc_TrnSendCommandData(void *obj, int cmd, int par, void *buf, int len)` | shared | `PostCommand` + `PostData` + `GetData(4)`. |

#### Серверный (`Fs_Trn*`)

| Функция | Где | Семантика |
|---|---|---|
| `Fs_TrnRunListener(void *handler, void *disc_cb)` | backend | Listener, accept-loop, per-conn thread. Не возвращает (кроме setup-ошибки). |
| `Fs_TrnGetCommand(void *obj, int *cmd, int *par)` | shared | Blocking read 8B. |
| `Fs_TrnGetData(void *obj, void *buf, int *len, int size)` | shared | Blocking read ровно `size` байт. |
| `Fs_TrnPostData(void *obj, void *buf, int len)` | shared | Async write N байт. |

### III.3. Контракты

**`obj`** — opaque handle. Один `obj` = одно соединение.

**`NULL obj`** — все функции возвращают ошибку, кроме `Fc_TrnDisconnect(NULL)` → `0`.

**`NULL buf` при `len > 0`** — `PostData` / `GetData` / `SendCommandData` возвращают ошибку, не вызывая транспорт.

**`*obj` при ошибке `Fc_TrnConnect`** — всегда `0`.

**`datalen` / `len`** — в байтах, везде.

**Return-value convention:** `-1` (0xFFFFFFFF) зарезервирован под transport errors в `Fc_TrnSendCommand`/`Fc_TrnSendCommandData`. Серверные handlers **не должны** возвращать `-1` как business reply.

**WSA refcount (только `TcpLink`):** `TcpLink` ctor/dtor, `WSAStartup`/`WSACleanup` под mutex, созданным один раз под `InterlockedCompareExchange` guard.

**Адрес (`Fc_TrnConnect`) — backend-specific:**
- `TcpLink`: `"host"` или `"host:port"`
- `PipeLink`: `NULL` → `\PIPE\FREEPM` (OS/2) / `\\.\pipe\FREEPM` (Win32)
- `ShmLink`: `NULL` → `\QUEUES\FREEPM`

### III.4. `F_Link` abstract interface

| Метод | Семантика |
|---|---|
| `Open()` | client: connect; server: create listener. Возврат 0 / -1. |
| `Accept(F_Link**)` | server: accept, allocate new `F_Link`, вернуть через `*ppNew`. |
| `Handshake()` | FreePM handshake. Таймаут — per-backend. Возврат 0 / `HAND_SHAKE_ERROR`. |
| `Send(const void*, int)` | Ровно `cbData` байт. Цикл на partial, EINTR-retry. |
| `Recv(void*, int*, int)` | Ровно `cbBuffer` байт. Peer-close → `*pcb` = прочитано, -1. |
| `Close()` | idempotent. |

**Handshake исполняется в `Fs_ClientThreadProc`**, не в accept-loop.

### III.5. Backend реализации

| Backend | Класс | Особенности |
|---|---|---|
| `pmtcp` | `TcpLink` | BSD sockets. Non-blocking connect + select с таймаутом. Handshake per-chunk timeout (`PMC_HANDSHAKE_TIMEOUT_MS = 3000`). WSA refcount в ctor/dtor. `SO_KEEPALIVE` включён, но без настройки. PMCLIENT PING — основной механизм liveness. `SD_SEND = 1` для OS/2. |
| `pmpipe` | `PipeLink` | OS/2 named pipes + Win32 эмуляция через `CreateNamedPipeA`. Byte mode. Client retries `DosOpen` on `ERROR_PIPE_BUSY` via `DosWaitNPipe`. Listener recovery: новый instance создаётся до hand-off. Cap: `FREEPM_PIPE_MAX_INST - 1` клиентов. Внутренние чанки `FREEPM_PIPE_OUTB_SIZE`/`INPB_SIZE = 0x8000` (32 KB) — прозрачны для API. |
| `pmshm` | `ShmLink` | OS/2 queues (уведомления) + shared memory (данные). Queue element = `{slot, length}` (8 байт). Handshake — `QmsHello {u8 version; u32 pid; u32 tid}` (9 байт) через `\QUEUES\FREEPM`. **Send/Recv разбивают и собирают сообщения произвольной длины на чанки `QMS_SLOT_SIZE = 1 MB`**; размер сообщения `QMS_SLOT_SIZE` не ограничен (recvBuf для reassembly). `QMS_SLOTS = 1` — один чанк in flight на направление. Recv peer-death — idle timeout 60s; Accept handshake — 30s. |

Платформенные различия поглощены `F_platform.h`. Backend-код использует только OS/2 API.

### III.6. Queue emulation (Win32)

`F_platform.h` эмулирует `Dos*Queue` через shared memory + named objects (Win32). Слот очереди = 16 байт (`WQ_MAX_ELEMENT`), `WQ_MAX_ELEMENTS = 8`. **Эмуляция — memory-only.**

**Очередь используется только в `pmshm`** — для control-сообщений (`QmsElem` 8B, `QmsHello` 9B). Данные в `pmshm` идут только через shared memory (см. §III.5). В `pmpipe` и `pmtcp` очередь не используется; данные — в pipe / TCP соответственно.

### III.7. Сборка backend

**Backend EXPORTS — 11 функций, identical ordinals 1–11:**

```
1  Fc_TrnConnect
2  Fc_TrnDisconnect
3  Fc_TrnPostCommand
4  Fc_TrnPostData
5  Fc_TrnSendCommand
6  Fc_TrnSendCommandData
7  Fc_TrnGetData
8  Fs_TrnRunListener
9  Fs_TrnPostData
10 Fs_TrnGetCommand
11 Fs_TrnGetData
```

**Клиент резолвит 1–7.** 8–11 — серверные. В `init.cpp::LoadBackend` — 7 `ResolveProc` в порядке 1–7.

## Часть IV. PMCLIENT — сессия (`Fc_Ses*`)

### IV.1. API

| Функция | Семантика |
|---|---|
| `Fc_SesConnect(char *address)` | Установить per-thread сессию: lazy backend load, `pfnFc_TrnConnect`, `pfnFc_TrnPostCommand(F_CMD_CLIENT_CONNECT, 0)`, `pfnFc_TrnGetData(F_CLIENTCONFIG)`, запись `aConns[tid]`. **Не более одного раза за жизнь потока.** При существующем слоте → `(APIRET)-1`. |
| `Fc_SesDisconnect(void)` | Best-effort `pfnFc_TrnPostCommand(F_CMD_CLIENT_EXIT)` → `pfnFc_TrnDisconnect(obj)` → очистка слота. Симметрично `Fc_SesConnect`. |
| `Fc_SesPostCommand(cmd, par)` | → `pfnFc_TrnPostCommand(aConns[tid].obj, ...)`. |
| `Fc_SesPostData(buf, len)` | → `pfnFc_TrnPostData(...)`. |
| `Fc_SesGetData(buf, len, max)` | → `pfnFc_TrnGetData(...)`. |
| `Fc_SesSendCommand(cmd, par)` | → `pfnFc_TrnSendCommand(...)`. |
| `Fc_SesSendCommandData(cmd, par, buf, len)` | → `pfnFc_TrnSendCommandData(...)`. |

Все 5 data-path функций возвращают `(APIRET)-1`, если `aConns[tid]` не в `SLOT_ACTIVE`.

### IV.2. `.def` PMCLIENT — 7 экспортов, ординалы 1–7

```
EXPORTS      = &
    Fc_SesPostCommand          .1, &
    Fc_SesPostData             .2, &
    Fc_SesGetData              .3, &
    Fc_SesSendCommand          .4, &
    Fc_SesSendCommandData      .5, &
    Fc_SesConnect              .6, &
    Fc_SesDisconnect           .7
```

Ординалы `.1`–`.5` сохранены за теми же по смыслу функциями (`Pmc*` → `Fc_Ses*`, 1-к-1). `.6`/`.7` — новые lifecycle-функции.

### IV.3. Хранение состояния

Всё — в PMCLIENT:

| Глобал | Назначение |
|---|---|
| `g_hmtxState` | защита `aConns`, `g_idClient`, `g_clientConfig`, `g_fInitialized`, backend-указателей |
| `aConns[FREEPM_MAX_THREADS]` | `{ tid, obj, state, reconnecting, lastActivity }` |
| `g_idClient` (под мьютексом) | process-wide, из первого CONNECT reply |
| `g_clientConfig` (под мьютексом) | `F_CLIENTCONFIG`, из первого CONNECT reply |
| `hmodBE` | handle backend DLL |
| `g_fInitialized` (под мьютексом) | init-complete флаг |
| `g_fKeepaliveRun`, `g_fTerminated` | volatile флаги потоков |

**В PMMERGE нет:** ни `obj`, ни HAB-таблицы, ни `idClient`, ни `F_CLIENTCONFIG`.

### IV.4. Состояния слота

`SLOT_FREE` (0) — слот не используется. `SLOT_ACTIVE` (1) — есть транспорт и `CONNECT`. `SLOT_BROKEN` (2) — транспорт потерян, reconnect в работе.

Переходы:
- `Fc_SesConnect` (успех) → `SLOT_ACTIVE`, `reconnecting = 0`.
- `Fc_SesDisconnect` → `SLOT_FREE`, `reconnecting = 0`.
- `OnTransportError(tid)` при `SLOT_ACTIVE && !reconnecting && !g_fTerminated` → `SLOT_BROKEN`, `reconnecting = 1`, `StartReconnect(tid)`.
- `ReconnectThreadProc(tid)` при успехе → `SLOT_ACTIVE`, `reconnecting = 0`. По истечении grace → `reconnecting = 0`, слот остаётся `SLOT_BROKEN`.

### IV.5. Keepalive / reconnect

**Keepalive** — один фоновый thread в PMCLIENT, запускается при первом успешном `Fc_SesConnect` (если `g_clientConfig.flConfig & F_CFG_PING_REQUIRED`). Интервал: `ulInactive / 2`, floor 5 с. Обходит `aConns[]`, для каждого `SLOT_ACTIVE` шлёт `pfnFc_TrnPostCommand(obj, F_CMD_CLIENT_PING, g_idClient)`. При ошибке → `OnTransportError(tid)`.

**Reconnect** — per-slot фоновый thread (`ReconnectThreadProc(tid)`). Интервал: `ulGrace / 3`, floor 1 с. Пробует `pfnFc_TrnConnect` + `F_CMD_CLIENT_RECONNECT(g_idClient)` + `pfnFc_TrnGetData(F_CLIENTCONFIG)`. При успехе — обновляет слот. По истечении `ulGrace` — слот остаётся `SLOT_BROKEN`.

**`Fc_SesConnect` не участвует в восстановлении.** При `SLOT_BROKEN` — `(APIRET)-1`.

### IV.6. Мьютекс и инициализация

`g_hmtxState` — безымянный `DosCreateMutexSem(NULL, &h, 0, FALSE)`, создаётся в `EnsureStateMutex` при первом `Fc_SesConnect`.

Race-safe без `DosEnterCritSec` (нет на Win32) и без `ERROR_ALREADY_EXISTS` (не определён на OS/2-таргете): оба потока могут создать по мьютексу; победитель записывается в `g_hmtxState`, проигравший handle закрывается. Никаких проверок кодов ошибок — только `0 / не-0`.

### IV.7. ABI-специфика

| Аспект | OS/2 | Win32 |
|---|---|---|
| `PMC_CB` (calling convention для `pfnFc_Trn*`) | `APIENTRY` | `__stdcall` (не `APIENTRY` — `__declspec(__pragma(...))` не работает в pointer declarators) |
| `_beginthread` | 4 аргумента | 3 аргумента |
| thread-процедура | `void fn(void *)` | `unsigned long __stdcall fn(void *)` |
| `DosEnterCritSec` / `DosExitCritSec` | есть | нет → `EnsureStateMutex` через create-with-race |

## Часть VI. Wire protocol

### VI.1. Framing

```
Fc_SesPostCommand(cmd, par):   cmd (4B) + par (4B)         = 8B header
Fc_SesPostData(buf, len):      buf (len B)                  = N data
Reply (header + payload):      FPM_RESP_HEADER (16B) + payload
```

Header всегда 8 байт: `cmd` (ULONG) + `par` (ULONG). `cmd` = `F_CMD_MAKE(class, opcode)`.

### VI.2. Handshake

Базовый F_Link handshake — 9 байт в обе стороны:
- Client → Server: `"pIpEtEsT\0"`
- Server → Client: `"PiPeTeSt\0"`

`pmshm` использует расширенный handshake: `QmsHello {u8 version; u32 pid; u32 tid}` (9 байт) через `\QUEUES\FREEPM`, эхо — те же 9 байт через C_. **Чтение — ровно 9 байт.**

### VI.3. Команды

| Class | Opcode | Семантика | Bootstrap? |
|---|---|---|---|
| CORE | `F_CMD_CLIENT_CONNECT` | Открыть per-thread сессию; reply = `F_CLIENTCONFIG` (16B) | **да** |
| CORE | `F_CMD_CLIENT_RECONNECT` | Резюм сессии; payload = `{tid}`; reply = `F_CLIENTCONFIG` (16B) | да |
| CORE | `F_CMD_CLIENT_PING` | Touch | нет |
| CORE | `F_CMD_CLIENT_EXIT` | Закрыть per-thread сессию (fire-and-forget) | нет |
| CORE | `F_CMD_DB_PRINT` / `F_CMD_FATAL_COMMON` | Debug | нет |
| WIN | `NWinInitialize` | Process+Thread+Hab (не bootstrap транспорта) | нет |
| WIN | `NWinTerminate` | Destroy Thread+Hab | нет |
| WIN | `NWinGetLastError` | Query lastError | нет |
| GPI | `NGpi*` | GPI dispatch | нет |
| GORDER | `OCODE_*` | GOCA passthrough (отложено) | нет |

**`cmd == 0` = close.** `Fs_ClientThreadProc` при `cmd == 0` завершает recv-loop. Клиенты не должны использовать `cmd == 0` как бизнес-команду.

### VI.4. `F_CMD_CLIENT_CONNECT` payload

```
data    = 0
payload = нет
reply   = F_CLIENTCONFIG (16 байт: idClient, ulInactive, ulGrace, flConfig)
```

### VI.5. `NWinInitialize` payload

```
data    = tid
payload = { ULONG clientid }   ; 0 для первого потока процесса
reply   = iHab (ulResult)
        + F_CLIENTCONFIG (только если clientid == 0)
```

`NWinInitialize` обрабатывается PMMERGE (WIN-класс). PMCLIENT только доставляет команду через `Fc_SesSendCommandData` и возвращает reply.

### VI.6. `NWinTerminate` payload

```
data    = iHab
payload = { ULONG tid }
reply   = ulResult = 1/0
```

### VI.7. `RECONNECT` payload

```
data    = idClient
payload = { ULONG tid }
reply   = F_CLIENTCONFIG (или error)
```

### VI.8. `datalen` / `len`

Байты, везде.

## Часть VII. Стратегия тестирования

### VII.1. Принцип

- **Транспортные тесты** (`test_<backend>.exe`) — изолированно от PMCLIENT. Готовы, проходят.
- **PMCLIENT-тесты** (`test_pmclient.exe`) — per-thread сессия.
- **Интеграционные тесты** (`pmtest.exe`) — с реальным PMSERVER.

### VII.2. Покрытие транспортных тестов (готово)

| Группа | pmtcp | pmpipe | pmshm |
|---|---|---|---|
| A. Fc_TrnConnect (NULL obj, bad address, refused) | ✅ | ✅ | ✅ |
| B. Lifecycle (connect/disconnect) | ✅ | ✅ | ✅ |
| C. NULL obj / NULL buf | ✅ | ✅ | ✅ |
| D. Round-trip (PostCommand, PostData, SendCommand, SendCommandData, GetData) | ✅ | ✅ | ✅ |
| E. Partial frames / peer-close | ✅ | ✅ | ✅ |
| F. Multi-conn (5 sequential) | ✅ | ✅ | ✅ |

**Сноска про pmshm:** `Send`/`Recv` в pmshm режут/собирают сообщения по `QMS_SLOT_SIZE = 1 MB`; reassembly-буфер (`recvBuf`) покрыт `test_multichunk_payload` (4 MB) и `test_large_payload` (64 KB) в `test_pmshm.cpp`. У pmtcp/pmpipe аналога нет — partial send/recv идёт тем же циклом `while (total < cbData)`, что и 16-байтный round-trip; отдельного код-пути, требующего отдельного теста, нет.

### VII.3. Покрытие PMCLIENT-тестов (следующий этап)

| Группа | Что проверяет |
|---|---|
| A. `Fc_SesConnect` базовый | connect → CONNECT → `F_CLIENTCONFIG` → slot ACTIVE → `Fc_SesDisconnect` |
| B. Повторный `Fc_SesConnect` | второй вызов с того же tid → `(APIRET)-1`, слот не тронут |
| C. Data path без connect | `Fc_SesPostCommand` без `Fc_SesConnect` → `(APIRET)-1` |
| D. Data path из N потоков | 3–5 потоков, изоляция слотов |
| E. `F_CLIENTCONFIG` process-wide | первый заполняет; второй сверяет `idClient`; mismatch → `-1` |
| F. Keepalive | `F_CFG_PING_REQUIRED` → keepalive-поток; сбой PING → `SLOT_BROKEN` |
| G. Reconnect | убить транспорт → reconnect-поток → `SLOT_ACTIVE` |
| H. `Fc_SesDisconnect` шлёт EXIT | `F_CMD_CLIENT_EXIT` уходит до закрытия транспорта |

### VII.4. Ограничения тестов

`Fc_SesConnect(NULL, ...)` запускает PMSERVER.EXE при отсутствии локального. В тестах использовать явный `address` (`"127.0.0.1:9876"`), чтобы PMCLIENT не пытался стартовать PMSERVER. Тест и test-backend-сервер в одном процессе.

### VIII.1. P0-фиксы (✅ включены)

## Часть X. Резюме

**Архитектура:** client-server. L4–L6 симметричны. L7 асимметричен. GOCA — L7-внутренний формат сервера.

**Именование:** `Fc_` / `Fs_` / `F_` + квалификатор (`Trn` / `Ses` / `Dbg` / `Wire`) + глагол (`Post` / `Send` / `Get` / `Connect` / `Disconnect` / `Run`).

**L4 Transport:** `F_Link` abstract + 3 backend (`TcpLink`, `PipeLink`, `ShmLink`). Одна DLL на backend, 11 экспортов, ординалы 1–11. Клиент резолвит 1–7.

**PMCLIENT:** per-thread модель. 7 экспортов, ординалы 1–7 (`.1`–`.5` — data path, `.6`–`.7` — lifecycle). Всё состояние — `aConns[tid]`, `g_idClient`, `g_clientConfig`, `hmodBE` — внутри PMCLIENT. Backend грузится лениво на первом `Fc_SesConnect`. Нет `DllMain`, нет `Fc_SesInit`, нет `atexit`.

**Контракты `Fc_SesConnect` / `Fc_SesDisconnect`:**
- `Fc_SesConnect` — один раз за жизнь потока; при существующем слоте → `-1`; первый успешный в процессе заполняет `g_clientConfig`/`g_idClient`; последующие сверяют `idClient`.
- `Fc_SesDisconnect` — best-effort `F_CMD_CLIENT_EXIT` → `pfnFc_TrnDisconnect` → очистка слота. Симметрично.

**PMMERGE:** `WinInitialize` → `Fc_SesConnect(NULL)` + `Fc_SesSendCommandData(NWinInitialize)` → HAB. `WinTerminate` → `Fc_SesSendCommandData(NWinTerminate)` + `Fc_SesDisconnect()`. HAB-таблица не ведётся.

**`pmshm`:** `QMS_SLOT_SIZE = 1 MB` — размер чанка; `Send`/`Recv` chunk/reassemble произвольной длины, размер сообщения не ограничен. `QMS_SLOTS = 1` — один чанк in flight на направление. Очередь несёт только control-сообщения; данные — только в shared memory.

**`pmpipe`:** byte-mode, chunking `0x8000` внутренний (прозрачно для API).

**`pmtcp`:** BSD sockets, chunking `PMC_MAX_SOCK_CHUNK` внутренний (прозрачно для API).

**Тесты:** транспортные — проходят; PMCLIENT per-thread — следующий этап.
