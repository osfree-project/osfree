## 3. Границы

**GPI прокидывается, GRE — нет.** Клиент шлёт высокоуровневые `Gpi*` (`F_CMD_GPI_DISPATCH`), сервер сам превращает их в `Gre*`. Клиент не знает про `Gre*`, `F_DC`, растеризатор.

**WndProc не прокидывается.** Клиент не шлёт `WndProc` на сервер. Для стандартных классов — тонкий прокси в PMMERGE > `F_CMD_CTL_PROC` > серверный `Server*WndProc`. Для кастомных — `WndProc` локально на клиенте.

**Win\* API прокидывается.** Клиент шлёт `F_CMD_WIN_*`, сервер управляет `pWND[]`.

# Часть II. Протокол

## 4. Транспорт

**MVP:** TCP loopback (`127.0.0.1:port`). Работает на всех платформах, легко отлаживать, поддерживает remote-клиент. Латентность ~10–50 ?s на loopback — приемлемо.

**Оптимизация:** pluggable через `pal_transport_*`:
- `pal_transport_tcp.c` — по умолчанию.
- `pal_transport_pipe.c` — PMPIPE (OS/2), named pipe (Windows), Unix socket (Linux).

## 5. Формат сообщений

Все сообщения — **заголовок + опциональный payload**. Фиксированный порядок байт (native, LE для MVP; BE-нормализация — отдельная задача).

```c
struct FPM_MSG_HEADER {
    ULONG   ulCommand;   /* F_CMD_* */
    ULONG   ulHandle;    /* HPS/HDC/HWND/HAB/... (зависит от команды) */
    ULONG   cbPayload;   /* размер payload в байтах */
    ULONG   ulFlags;     /* зарезервировано, 0 */
};
/* payload следует за заголовком, cbPayload байт */
```

Ответ:

```c
struct FPM_RESP_HEADER {
    ULONG   ulStatus;    /* 0 = ok, иначе PMERR_* или APIRET */
    ULONG   ulResult;    /* возвращаемое значение (LONG/BOOL/HANDLE) */
    ULONG   cbPayload;   /* размер payload (например, для Query*) */
    ULONG   ulLastError; /* per-connection last error */
};
```

## 7. `F_CMD_GPI_DISPATCH` — generic dispatcher для `Gpi*`

Аналог `Gre32EntryN`. Одна команда для всех `Gpi*`. Код функции — в payload.

**Запрос:**
```
HEADER: command=F_CMD_GPI_DISPATCH, handle=hps, cbPayload=sizeof(FPM_GPI_CALL)+cbArgs
payload:
  struct FPM_GPI_CALL {
      ULONG   ulFnCode;    /* N_GpiLine, N_GpiSetColor, ... */
      ULONG   cbArgs;      /* размер упакованных аргументов */
      ULONG   ulFlags;     /* зарезервировано */
      BYTE    abArgs[];    /* упакованные аргументы (см. ниже) */
  };
```

**Ответ:**
```
HEADER: command=F_CMD_GPI_DISPATCH, status=0
payload:
  ULONG   ulResult;   /* LONG/BOOL/HANDLE — приводится к ULONG */
  ULONG   ulLastError;/* PMERR_* если статус != 0 */
```

**Коды функций (`gpi_wire.h`):**

```c
#define N_GpiLine              0x0001
#define N_GpiPolyLine          0x0002
#define N_GpiPolyLineDisjoint  0x0003
#define N_GpiSetColor          0x0004
#define N_GpiQueryColor        0x0005
#define N_GpiBox               0x0006
#define N_GpiFullArc           0x0007
#define N_GpiPartialArc        0x0008
#define N_GpiMove              0x0009
#define N_GpiSetCurrentPosition 0x000A
#define N_GpiQueryCurrentPosition 0x000B
#define N_GpiCharStringAt      0x000C
#define N_GpiCharString        0x000D
#define N_GpiCreatePS          0x000E
#define N_GpiDestroyPS         0x000F
#define N_GpiAssociate         0x0010
#define N_GpiOpenSegment       0x0011
#define N_GpiCloseSegment      0x0012
#define N_GpiDrawSegment       0x0013
#define N_GpiDrawChain         0x0014
#define N_GpiGetData           0x0015
#define N_GpiPutData           0x0016
/* ... ~200 кодов, генерируются из pmgpi.h ... */
```

**Маршалинг аргументов:** per-function. `GpiLine(HPS, PPOINTL)` упаковывает `POINTL` в `abArgs`. `GpiSetColor(HPS, LONG)` упаковывает `LONG`. `GpiCharStringAt(HPS, PPOINTL, LONG, PCH)` упаковывает `POINTL + LONG + cch + string`. Указатели на клиентские данные **не передаются** — передаётся содержимое.

**Почему не per-function команды:** протокол не растёт с каждой функцией. Enum команд остаётся постоянным (~40). `switch` локализован в `DispatchGpi` (сервер) и в `GpiDispatch` (клиент).

## 8. `F_CMD_CTL_PROC` — generic dispatcher для `WndProc`

Аналог `somDispatch` в DSOM. Одна команда для всех стандартных `WndProc`.

**Запрос:**
```
HEADER: command=F_CMD_CTL_PROC, handle=hwnd, cbPayload=sizeof(FPM_CTL_CALL)
payload:
  struct FPM_CTL_CALL {
      ULONG   msg;
      MPARAM  mp1;
      MPARAM  mp2;
  };
```

**Ответ:**
```
HEADER: command=F_CMD_CTL_PROC, status=0
payload:
  MRESULT mres;
  ULONG   ulLastError;
```

**Сервер:**
```c
case F_CMD_CTL_PROC:
    F_RecvDataFromClient(obj, &call, &len, sizeof(call));
    /* если override — F_CMD_SUBCLASS_CALL (см. ниже) */
    mres = DispatchToServerWndProc(pWND[hwnd].class, hwnd, call.msg, call.mp1, call.mp2);
    SendResponse(obj, mres, ...);
```

`DispatchToServerWndProc` — `switch (pWND[hwnd].class)`:
```c
switch (class) {
case WC_STATIC:      return ServerStaticWndProc(hwnd, msg, mp1, mp2);
case WC_BUTTON:      return ServerButtonWndProc(hwnd, msg, mp1, mp2);
case WC_ENTRYFIELD:  return ServerEntryFieldWndProc(hwnd, msg, mp1, mp2);
case WC_FRAME:       return ServerFrameWndProc(hwnd, msg, mp1, mp2);
case WC_TITLEBAR:    return ServerTitleBarWndProc(hwnd, msg, mp1, mp2);
case WC_MENU:        return ServerMenuWndProc(hwnd, msg, mp1, mp2);
/* ... */
default:             return ServerGenericDefWindowProc(hwnd, msg, mp1, mp2);
}
```

## 9. `F_CMD_SUBCLASS_CALL` — override

Когда приложение вызвало `WinSubclassWindow(hwnd, MyProc)` для стандартного контрола, сервер при каждом сообщении для `hwnd`:

1. Если `pWND[hwnd].fOverride` — шлёт клиенту `F_CMD_SUBCLASS_CALL` с `(hwnd, msg, mp1, mp2)`.
2. Клиент вызывает `MyProc`, получает `mres`.
3. Клиент возвращает `(mres, handled_flag)`:
   - `handled = TRUE` — сервер использует `mres`, стандартную обработку не запускает.
   - `handled = FALSE` — сервер использует свой `mres` от `Server*WndProc`, клиентский `mres` игнорирует.

**Запрос (сервер > клиент):**
```
HEADER: command=F_CMD_SUBCLASS_CALL, handle=hwnd
payload: FPM_CTL_CALL { msg, mp1, mp2 }
```

**Ответ (клиент > сервер):**
```
HEADER: command=F_CMD_SUBCLASS_CALL
payload: struct { MRESULT mres; ULONG fHandled; }
```

**Стоимость:** 1 IPC на сообщение для overridden контрола. Для не-overridden — 0.

## 10. `F_CMD_DEFWINDOWPROC`

`WinDefWindowProc(hwnd, msg, mp1, mp2)` на клиенте > `F_CMD_DEFWINDOWPROC` > сервер:

```c
case F_CMD_DEFWINDOWPROC:
    F_RecvDataFromClient(obj, &call, &len, sizeof(call));
    if (IsStandardClass(pWND[hwnd].class))
        mres = DispatchToServerWndProc(pWND[hwnd].class, hwnd, msg, mp1, mp2);
    else
        mres = ServerGenericDefWindowProc(hwnd, msg, mp1, mp2);
    SendResponse(obj, mres, ...);
```

**1 IPC.** Приложение, чей `MyButtonProc` вызывает `WinDefWindowProc` для необработанных, получает цепочку к `ServerButtonWndProc` через сервер. Семантика OS/2 сохранена.

## 11. `F_CMD_SET_OVERRIDE`

`WinSubclassWindow(hwnd, MyProc)` на клиенте:
1. Локально: `pOldProc = windows[hwnd].WndProc; windows[hwnd].WndProc = MyProc`.
2. 1 IPC: `F_CMD_SET_OVERRIDE` с `hwnd` > сервер ставит `pWND[hwnd].fOverride = TRUE`.

`WinSubclassWindow(hwnd, original)` (отмена):
1. Локально восстановить `WndProc`.
2. 1 IPC: `F_CMD_SET_OVERRIDE` > `pWND[hwnd].fOverride = FALSE`.

## 12. `F_CMD_WIN_GETMSG`

Клиент: `WinGetMsg(hab, &qmsg, 0, 0, 0)`.
Запрос: `F_CMD_WIN_GETMSG`, `handle=ihab`.
Ответ (если есть сообщение): `QMSG` в payload, `status=0`. Если нет — `status=PMERR_NO_MSG`, `cbPayload=0`.

**Блокирующий vs неблокирующий:** `WinGetMsg` без `PM_REMOVE` — peek; с `PM_REMOVE` — блокируется до появления сообщения. Для блокирующего режима сервер держит запрос в очереди и отвечает при появлении сообщения (или по таймауту). Для MVP — **неблокирующий**: клиент сам крутит цикл `WinPeekMsg` + sleep. `WinGetMsg` = `WinPeekMsg` + retry. Позже — блокирующий через `poll`/`select`.

## 13. `F_CMD_WIN_BEGINPAINT` / `F_CMD_WIN_ENDPAINT`

**BeginPaint:**
```
Клиент: WinBeginPaint(hwnd, &ps) > F_CMD_WIN_BEGINPAINT, handle=hwnd
Сервер: 
  hps = GpiCreatePS(NULL, pWND[hwnd].hdc, &sizl, 0);   // PMGPI
  GpiAssociate(hps, pWND[hwnd].hdc);
  /* clip = update region */
  GpiSetClipRegion(hps, ...);                          // PMGPI
  ответ: HPS в payload
```

**EndPaint:**
```
Клиент: WinEndPaint(&ps) > F_CMD_WIN_ENDPAINT, handle=hps
Сервер:
  GpiDestroyPS(hps);                                    // PMGPI
  /* перерисовать: blit pVBuffmem > screen */
  pal_driver_blit(...);
  ответ: status
```

**Ключевое:** сервер рисует в `pVBuffmem` (через `F_DC.pTarget`), `WinEndPaint` делает blit. Клиент не рисует — только шлёт `Gpi*` через `F_CMD_GPI_DISPATCH`.

## 14. Обработка ошибок

**На сервере:** `WinSetErrorInfo(err)` (osFree) > compat shim > `pal_set_error(pConn, err)` > `pConn->lastError`.

**В ответе:** `FPM_RESP_HEADER.ulLastError = pConn->lastError`.

**На клиенте:** `WinGetLastError(hab)` возвращает `errorState.lastError`, который клиент обновляет из `ulLastError` каждого ответа.

**Семантика:** per-connection, не глобальная. Каждый клиент видит свои ошибки.

## 15. Endianness

**MVP:** обе стороны — little-endian (x86/x64/ARM-LE). Нормализация не делается.

**Позже:** `pal_htonl`/`pal_ntohl` в сериализаторах, wire-формат — network byte order. Отдельная задача.

# Часть III. Прокси

## 16. Gpi* прокси (`pmgpi/client/F_GPI.cpp`)

Per-function stubs, генерируются из `pmgpi.h`. Каждый stub упаковывает аргументы и вызывает `GpiDispatch`.

```c
/* Общий диспетчер */
static ULONG GpiDispatch(HPS hps, ULONG ulFnCode,
                         const void *pArgs, ULONG cbArgs)
{
    struct { ULONG ulFnCode; ULONG cbArgs; ULONG ulFlags; } call = {
        ulFnCode, cbArgs, 0
    };
    F_SendCmdToServer(client_obj, F_CMD_GPI_DISPATCH, (ULONG)hps);
    F_SendDataToServer(client_obj, &call, sizeof(call));
    if (cbArgs) F_SendDataToServer(client_obj, pArgs, cbArgs);
    struct { ULONG ulResult; ULONG ulLastError; } resp;
    F_RecvDataFromServer(client_obj, &resp, &len, sizeof(resp));
    errorState.lastError = resp.ulLastError;
    return resp.ulResult;
}

/* Сгенерированные stubs */
LONG F_GpiLine(HPS hps, PPOINTL pptl)
{
    POINTL pt = *pptl;
    return (LONG)GpiDispatch(hps, N_GpiLine, &pt, sizeof(pt));
}

BOOL F_GpiSetColor(HPS hps, LONG lColor)
{
    return (BOOL)GpiDispatch(hps, N_GpiSetColor, &lColor, sizeof(lColor));
}

BOOL F_GpiBox(HPS hps, LONG lControl, PPOINTL pptl, LONG lHRound, LONG lVRound)
{
    struct { LONG lControl; POINTL pt; LONG lHRound; LONG lVRound; } args = {
        lControl, *pptl, lHRound, lVRound
    };
    return (BOOL)GpiDispatch(hps, N_GpiBox, &args, sizeof(args));
}

LONG F_GpiCharStringAt(HPS hps, PPOINTL pptl, LONG lCount, PCH pchString)
{
    /* переменный размер: POINTL + LONG + cch + строка */
    ULONG cb = sizeof(POINTL) + sizeof(LONG) + (ULONG)lCount;
    PBYTE buf = alloca(cb);
    memcpy(buf, pptl, sizeof(POINTL));
    memcpy(buf + sizeof(POINTL), &lCount, sizeof(LONG));
    memcpy(buf + sizeof(POINTL) + sizeof(LONG), pchString, (ULONG)lCount);
    return (LONG)GpiDispatch(hps, N_GpiCharStringAt, buf, cb);
}
```

**Генератор** (`tools/gen_proxies.py`):
1. Парсит `pmgpi.h` — прототипы `Gpi*`.
2. Для каждой функции генерирует `N_GpiXxx` в `gpi_wire.h` и stub в `F_GPI.cpp`.
3. Для структур (`POINTL`, `RECTL`, `FIXED`) — генерирует сериализаторы.
4. Для функций с `PBYTE`/`PCH` — генерирует упаковку с длиной.

**Не генерируются:** `GpiCreatePS`, `GpiDestroyPS`, `GpiAssociate` (особые, см. ниже), `GpiGetData`/`GpiPutData` (переменный размер, но генерируются с кастомным marshaling).

static MRESULT F_ProxyCall(HWND hwnd, ULONG msg, MPARAM mp1, MPARAM mp2)

# Итог

**Архитектура:** PMGPI + PMGRE + PMWIN-менеджер + стандартные WndProc — на сервере. Gpi*-прокси + Win*-прокси + WndProc-прокси + 16-bit thunks — на клиенте. PAL — между сервером и ОС. Транспорт pluggable (TCP MVP). Драйвер pluggable (SDL MVP).

**Протокол:** `F_CMD_GPI_DISPATCH` (generic dispatcher для `Gpi*`, аналог `Gre32EntryN`), `F_CMD_CTL_PROC` (generic dispatcher для стандартных `WndProc`, аналог `somDispatch`), per-function `F_CMD_WIN_*`, `F_CMD_SUBCLASS_CALL` для override. Протокол компактный, не растёт с числом функций.

**Прокси:** per-function stubs для `Gpi*` (генерируются из `pmgpi.h`), тонкие `PROXY_WNDPROC` для стандартных `WndProc` (шаблон), per-function `F_Win*` для `Win*`, 16-bit thunks (Фаза 8, только клиент).

**План:** 0 (багфиксы) > 0.5 (PAL) > 1 (каркас) > 2 (PMGRE) > 3 (протокол GPI) > 4 (Window Manager) > 5 (D3) > 6 (драйвер) > 7 (тесты) > 8 (16-bit). MVP — 5–6 месяцев, полный — 7–9 месяцев.

**Модель:** DSOM, адаптированная к процедурному API PM. Прокси на клиенте, target на сервере, location transparency сохранена, ABI совместим с OS/2 на уровне символов и сигнатур. Сервер кросс-платформенный, клиент OS/2-специфичный.


# PMGPI.DLL (клиент) на OpenWatcom 1.9 / C89

Хорошая фиксация. OpenWatcom 1.9 + C89 накладывает конкретные ограничения — их надо учесть в дизайне и генераторе, иначе потом переписывать.

---

## 1. Ограничения C89, которые бьют по коду

| Ограничение | Что нельзя | Замена |
|---|---|---|
| Нет `//` комментариев | `// comment` | `/* comment */` |
| Нет смешанных деклараций | `stmt; int x;` | Все декларации в начале блока |
| Нет `inline` | `inline int f()` | `static` в заголовке или отдельный `.c` |
| Нет `alloca` (стандартного) | `alloca(n)` | Фиксированный стек-буфер или `malloc`/`free` |
| Нет `stdint.h` | `int32_t` | `LONG`, `ULONG`, `USHORT`, `BOOL` из `<os2.h>` |
| Нет `bool` | `bool` | `BOOL` (`TRUE`/`FALSE`) |
| Нет variadic macros | `#define F(...) __VA_ARGS__` | Отдельные макросы или функции |
| Нет `long long` | `int64_t` | Не нужен для 32-битного API |
| Нет designated initializers | `{.x=1}` | `{1}` |
| Нет compound literals | `f((POINTL){1,2})` | `{ POINTL pt = {1,2}; f(&pt); }` |
| Нет `for (int i...)` | `for (int i = 0; ...)` | `int i; for (i = 0; ...)` |

**`_alloca` в Watcom есть** (`#include <malloc.h>`), но это расширение, а не C89. Для строгого C89 — не используем. Для MVP — фиксированный стек-буфер с проверкой размера.

## 4. Транспорт: PMPIPE через OpenWatcom

В FreePM уже есть `PMPIPE` backend (`F_pipe.cpp`, `F_pipe.hpp` — не показаны в этом чате, но подразумеваются). Для MVP используем его — это нативный OS/2 pipe, быстрее TCP.

Функции транспорта (уже есть в FreePM):
```c
APIRET F_SendCmdToServer(ULONG obj, int cmd, int par);
APIRET F_SendDataToServer(ULONG obj, void *data, int len);
APIRET F_RecvDataFromServer(ULONG obj, void *data, int *len, int maxlen);
```

**Они уже C89-совместимы** (объявления в начале, нет `inline`, нет `alloca`). Менять не надо.

Для MVP **TCP не нужен** — сервер на той же OS/2 машине, PMPIPE достаточно. TCP — Фаза G (кросс-платформенный сервер), после PAL.

Это упрощает Фазу A: не надо тащить TCP в клиент.

## 5. `GpiDispatch` — C89

```c
/* gpi_entry.c */
#include <os2.h>
#include <pmgpi.h>
#include "gpi_wire.h"
#include "transport.h"
#include "error.h"

#define FPM_MAX_STACK_ARGS  512

static ULONG GpiDispatch(HPS hps, ULONG ulFnCode,
                         const void *pArgs, ULONG cbArgs)
{
    ULONG   ahdr[3];
    ULONG   result;
    ULONG   lastError;
    int     len;
    APIRET  rc;

    ahdr[0] = ulFnCode;
    ahdr[1] = cbArgs;
    ahdr[2] = 0;

    rc = F_SendCmdToServer(client_obj, F_CMD_GPI_DISPATCH, (ULONG)hps);
    if (rc != 0) {
        SetLastError(FPMERR_TRANSPORT);
        return (ULONG)GPI_ERROR;
    }
    rc = F_SendDataToServer(client_obj, (void *)ahdr, sizeof(ahdr));
    if (rc != 0) { /* ... */ }
    if (cbArgs != 0) {
        rc = F_SendDataToServer(client_obj, (void *)pArgs, (int)cbArgs);
        if (rc != 0) { /* ... */ }
    }

    len = 0;
    rc = F_RecvDataFromServer(client_obj, &result, &len, sizeof(result));
    if (rc != 0 || len != (int)sizeof(result)) {
        SetLastError(FPMERR_TRANSPORT);
        return (ULONG)GPI_ERROR;
    }
    len = 0;
    rc = F_RecvDataFromServer(client_obj, &lastError, &len, sizeof(lastError));
    if (rc == 0 && len == (int)sizeof(lastError))
        SetLastError((APIRET)lastError);

    return result;
}
```

**Все декларации в начале.** Нет `//`. Нет `alloca`. Нет `inline` (`static` — по умолчанию в C89). Ок.

## 6. Генерируемые stubs — C89

Для простых функций (`GpiLine`, `GpiSetColor`):

```c
/* gpi_proxies.c — генерируется */
LONG APIENTRY F_GpiLine(HPS hps, PPOINTL pptl)
{
    POINTL pt = *pptl;
    return (LONG)GpiDispatch(hps, N_GpiLine, &pt, sizeof(pt));
}

BOOL APIENTRY F_GpiSetColor(HPS hps, LONG lColor)
{
    return (BOOL)GpiDispatch(hps, N_GpiSetColor, &lColor, sizeof(lColor));
}

BOOL APIENTRY F_GpiBox(HPS hps, LONG lControl, PPOINTL pptl,
                       LONG lHRound, LONG lVRound)
{
    struct {
        LONG    lControl;
        POINTL  pt;
        LONG    lHRound;
        LONG    lVRound;
    } args;
    args.lControl = lControl;
    args.pt       = *pptl;
    args.lHRound  = lHRound;
    args.lVRound  = lVRound;
    return (BOOL)GpiDispatch(hps, N_GpiBox, &args, sizeof(args));
}
```

Для функций с переменной длиной (`GpiCharStringAt`, `GpiGetData`, `GpiPutData`) — фиксированный стек-буфер + проверка размера:

```c
#define FPM_MAX_INLINE_ARGS 1024

LONG APIENTRY F_GpiCharStringAt(HPS hps, PPOINTL pptl, LONG cch, PCH pch)
{
    struct {
        POINTL  pt;
        LONG    cch;
    } fix;
    ULONG   cbArgs;
    ULONG   ahdr[3];
    PBYTE   pBuf;
    LONG    result;
    int     len;
    APIRET  rc;

    fix.pt  = *pptl;
    fix.cch = cch;
    cbArgs  = (ULONG)sizeof(fix) + (ULONG)cch;

    /* Если строка помещается в стек — используем стек */
    if (cbArgs <= FPM_MAX_INLINE_ARGS) {
        BYTE  abStack[FPM_MAX_INLINE_ARGS];
        memcpy(abStack, &fix, sizeof(fix));
        memcpy(abStack + sizeof(fix), pch, (ULONG)cch);
        /* send: header + abStack */
        /* ... */
    } else {
        pBuf = (PBYTE)malloc(cbArgs);
        if (pBuf == NULL) { SetLastError(PMERR_INSUFFICIENT_MEMORY); return GPI_ERROR; }
        memcpy(pBuf, &fix, sizeof(fix));
        memcpy(pBuf + sizeof(fix), pch, (ULONG)cch);
        /* send: header + pBuf */
        /* ... */
        free(pBuf);
    }
    return result;
}
```

**Без `alloca`.** Стек-буфер фиксированного размера, для больших — `malloc`. C89.

**Генератор** должен уметь распознавать:
- Скалярные аргументы (`LONG`, `ULONG`, `BOOL`, `FIXED`, `HPS`, `HDC`, …) — copy by value.
- Структуры фиксированного размера (`POINTL`, `RECTL`, `SIZEL`, `FATTRS`, `ARCPARAMS`, …) — `memcpy` в `args`.
- `P<struct>` — разыменовать один раз, скопировать структуру.
- `PBYTE`/`PCH` + отдельный `LONG cch`/`LONG cbData` — переменный размер, стек-буфер + `malloc` fallback.
- `PVOID` + размер — аналогично.

Это ~5 категорий. Генератор обрабатывает каждую.

## 7. `.def` файл — экспорты + ординалы

**Ординалы должны совпадать с OS/2 PMGPI.DLL.** Их надо взять из реальной OS/2 PMGPI.DLL:

```cmd
impdef pmgpi.ref > pmgpi_ordinals.txt
```

Формат:
```
LIBRARY PMGPI INITINSTANCE TERMINSTANCE
DESCRIPTION 'FreePM PMGPI client proxy'
PROTMODE
EXPORTS
    GpiAbortPath        @100
    GpiAssociate        @101
    GpiBeginArea        @102
    GpiBeginElement     @103
    GpiBeginPath        @104
    GpiBitBlt           @105
    ; ... ~200 записей
```

**Генератор `gen_def.py`** берёт `pmgpi_ordinals.txt` (снятый с реальной PMGPI.DLL) + `pmgpi.h` (проверяет, что все `Gpi*` из `pmgpi.h` есть в ordinals) > `pmgpi.def`.

Если ординал отсутствует в реальной DLL (новая функция, `Gpi*` из APILEVEL > 2) — назначаем следующий свободный (после максимума).

**Проверка:** `exehdr pmgpi.dll > our_exports.txt`, сравнить с `pmgpi.ref`. Расхождения — ошибка.

**Альтернатива без ординалов:** если приложения линкуются по имени (`GpiLine`, а не `@105`), можно без ординалов. Но OS/2-приложения **исторически линкуются по ординалам**, и `Wlink` может это требовать. Для MVP — с ординалами, это гарантия.

## 8. `wmakefile` (клиент)

```makefile
# pmgpi/client/wmakefile
CC      = wcc386
CFLAGS  = -bt=os2 -bm -bd -5s -ox -w4 -zq -i..\common -i..\client
LD      = wlink
LDFLAGS = system os2v2_dll initinstance terminstance name PMGPI

OBJS = gpi_entry.obj gpi_proxies.obj transport.obj error.obj

all: pmgpi.dll

pmgpi.dll: $(OBJS) pmgpi.def
    $(LD) $(LDFLAGS) file {$(OBJS)} @pmgpi.def

gpi_entry.obj: gpi_entry.c gpi_wire.h transport.h error.h

gpi_proxies.obj: gpi_proxies.c gpi_proxies.h gpi_wire.h

# ... остальные

clean: .SYMBOLIC
    -del *.obj
    -del pmgpi.dll
```

Флаги:
- `-bt=os2` — target OS/2
- `-bm` — multi-thread safe
- `-bd` — DLL
- `-5s` — Pentium, stack-based calling
- `-ox` — optimize
- `-w4` — warnings
- `-zq` — quiet

Для отладки — `-d2` и `-hw` (Watcom debugger).

## 10. Генератор `gen_proxies.py` — что парсит

Вход: `pmgpi.h` (из OpenWatcom OS/2 toolkit).

Парсит:
```

Выход:

- `gpi_proxies.c` — `F_Gpi*` stubs (C89).
- `gpi_proxies.h` — прототипы `F_Gpi*`.
- `server_stub/dispatch.c` — `DispatchGpi` switch (C89).
- `pmgpi.def` — экспорты + ординалы.

**Тип-маппинг** (C89):
| Тип в `pmgpi.h` | Категория | Маршалинг |
|---|---|---|
| `LONG`, `ULONG`, `BOOL`, `FIXED`, `HPS`, `HDC`, `HBITMAP`, `HRGN`, `HAB`, `HMF`, `HPAL`, `LONG32` | scalar | by value |
| `POINTL`, `RECTL`, `SIZEL`, `SIZEF`, `MATRIXLF`, `ARCPARAMS`, `FATTRS`, `FONTMETRICS`, `KERNINGPAIRS`, `BITMAPINFOHEADER2` | struct | `memcpy` в `args` |
| `P<struct>` (`PPOINTL`, `PRECTL`, …) | ptr-to-struct | разыменовать, `memcpy` |
| `PCH`, `PSTR8`, `PSZ`, `PBYTE` + отдельный `LONG cch`/`LONG cb` | var-len | стек-буфер + `malloc` fallback |
| `PVOID` + `ULONG cb` | var-len | как выше |
| `PVOID` без размера (`pCtlData`, `pPresParams`) | opaque | **не маршалится** — для `Gpi*` таких нет, только для `Win*` |

**Хорошая новость:** `Gpi*` почти все попадают в первые 3 категории. Var-len — только `GpiCharString*`, `GpiGetData`, `GpiPutData`, `GpiElement`, `GpiComment`, `GpiQueryElement`, `GpiImage`, `GpiDrawBits`, `GpiSetBitmapBits`, `GpiQueryBitmapBits`. ~10 функций. Обрабатываются вручную или генератором с шаблоном.

## 11. ABI-верификация — конкретные шаги

1. **Собрать PMGPI.DLL** через `wmake`.
2. **Снять экспорты** нашего DLL:
   ```
   exehdr pmgpi.dll > our_exports.txt
   ```
3. **Снять экспорты** реального OS/2 PMGPI.DLL:
   ```
   exehdr pmgpi.ref > ref_exports.txt
   ```
4. **Сравнить** ординалы и имена (скрипт `compare_exports.py`).
5. **Проверить сигнатуры** — `impdef` нашего DLL, сравнить с `pmgpi.h`.
6. **Слинковать тестовое приложение** (простое, вызывает `GpiLine`, `GpiSetColor`, `GpiCreatePS`) с нашим PMGPI.LIB.
7. **Запустить** с stub-сервером. Ожидаемо: `GpiLine` > `GPI_ERROR`, `GpiCreatePS` > `NULLHANDLE`, но **без крашей**.
8. **Запустить с реальным OS/2** (если есть) — наша DLL подменяет системную, приложение работает как обычно.

## 14. Ключевые C89-ловушки для этого кода

1. **`static` функции в заголовке** — нельзя (C89 `inline` нет). Если нужна inline-подобная функция, либо `static` в `.c` (не в `.h`), либо `#define`-макрос.
2. **`alloca`** — не использовать. Стек-буфер `BYTE abStack[N]` с проверкой размера.
3. **`//`** — не использовать. Только `/* */`.
4. **Смешанные декларации** — `int x; stmt; int y;` — нельзя. Все `int` в начале функции.
5. **`for (int i...)`** — нельзя. `int i; for (i = ...)`.
6. **`PBYTE` + размер** — переменный размер, `memcpy` + `malloc` fallback.
7. **`_System` vs `__stdcall`** — в Watcom `APIENTRY` = `_System`. Для `Gpi*` — `APIENTRY`, для внутренних `F_Gpi*` — `_System` (тот же). Проверить, что в `pmgpi.h` OS/2 toolkit `Gpi*` объявлены с `APIENTRY` (они так и есть).
8. **`PACK`** — структуры (`POINTL`, `RECTL`) в `os2.h` уже упакованы `#pragma pack(1)`? Проверить. Если нет — `#pragma pack(1)` вокруг `struct` в `args`.
9. **`__cdecl` vs `_System`** — `Gpi*` в OS/2 = `_System`. Не `__cdecl`. Ошибка здесь = краш на первом вызове.
10. **Ординалы** — `EXPORTS` в `.def` с `@N`. Без `@N` — экспорт по имени, приложение слинкуется, но не с реальным OS/2 DLL.

## Итог

**Клиентский PMGPI.DLL на OpenWatcom 1.9 / C89 — реализуемо за ~2 недели.** Ключевые решения:

1. **PMPIPE, не TCP** — уже есть в FreePM, нативно на OS/2. TCP — Фаза G (кросс-платформенный сервер).
2. **Генератор** `gen_proxies.py` — покрывает ~190 из ~200 `Gpi*`. Руками — `GpiCreatePS`/`DestroyPS`/`Associate`, `GpiGetData`/`PutData`, `GpiCharString*` (var-len).
3. **C89-совместимый вывод генератора** — все декларации в начале, `/* */`, без `inline`, без `alloca` (стек-буфер + `malloc` fallback).
4. **`.def` с ординалами** — снимаются с реальной OS/2 PMGPI.DLL через `exehdr`, сверяются.
5. **Stub-сервер** — `DispatchGpi` с `return GPI_ERROR` для всех, ~200 строк, генерируется.
6. **ABI-верификация** — `exehdr` сравнение, линковка тестового приложения, запуск с stub-сервером (без крашей).
7. **16-bit thunks** — Фаза H, не в MVP.

После Фазы A PMGPI.DLL **не меняется** — только сервер наращивается (Фазы B–G). Это и есть ценность стратегии: клиент стабилен, ABI зафиксирован, сервер развивается независимо.

# PMCLIENT.DLL как транспорт клиента — принято

Это снимает необходимость в TCP-транспорте на стороне клиента. Клиент PMGPI.DLL не знает про сокеты, framing, переподключение — всё это внутри PMCLIENT.DLL. PMGPI.DLL вызывает функции PMCLIENT.DLL, как `F_GPI.cpp` в FreePM вызывает `F_SendGenCmdDataToServer`.

## Что я знаю из кода FreePM (факты, не догадки)

Из `init.cpp`, `F_hab.cpp`, `F_debug.cpp`, `windowmgr.cpp`, `F_GPI.cpp`, `Fs_main.cpp`:

| Функция | Сигнатура (как используется) | Сторона |
|---|---|---|
| `InitServerConnection` | `APIRET (char *remotemachineName, ULONG *obj)` | клиент |
| `CloseServerConnection` | `APIRET (void)` | клиент |
| `startServerThreads` | `APIRET (void *handl)` | клиент (запускает серверные потоки в backend) |
| `F_SendCmdToServer` | `APIRET (ULONG obj, int cmd, int data)` | клиент |
| `F_SendDataToServer` | `APIRET (ULONG obj, void *data, int len)` | клиент |
| `F_RecvDataFromServer` | `APIRET (ULONG obj, void *data, int *len, int maxlen)` | клиент |
| `F_SendGenCmdToServer` | `APIRET (ULONG obj, int cmd, int par)` | клиент |
| `F_SendGenCmdDataToServer` | `APIRET (ULONG obj, int cmd, int par, void *data, int datalen)` | клиент |

## Что я не знаю и не буду придумывать

Это вопросы, ответы на которые нужны для дизайна `GpiDispatch`:

1. **`F_SendGenCmdToServer` / `F_SendGenCmdDataToServer` — делают ли round-trip?** В `Win32GetPS` результат `F_SendGenCmdToServer` кастуется к `HPS` и возвращается без `F_RecvDataFromServer`. В `F_GpiSetColor` — аналогично. Если эти функции делают send + recv + возвращают результат, то для getters (где нужен payload) их недостаточно. Если только send — то код в `Win32GetPS`/`F_GpiSetColor` неполный.

2. **`datalen` в `F_SendGenCmdDataToServer` — байты или int'ы?** В `F_GpiSetColor`: `_F_SendGenCmdDataToServer(F_CMD_GPI_SET_COLOR, hps, (void *)&lColor, 1)` — для `LONG` передан `1`. Если байты, то это ошибка (должно быть 4). Если int'ы — 1 = 4 байта. Нужна спецификация.

3. **`_F_SendGenCmdDataToServer` (с подчёркиванием)** — это отдельная функция, макрос или локальная обёртка? В `F_GpiSetColor`/`F_GpiLine` используется именно она, с сигнатурой `(cmd, par, data, datalen)` — без `obj`. Нужно определение.

4. **Формат сообщения** — PMCLIENT.DLL сам обрамляет (заголовок, длина, выравнивание)? Или клиент должен слать заголовок явно? Из `Fs_main.cpp::handler` видно, что сервер получает `ncmd`, `data`, потом payload — значит, обрамление есть, и оно внутри PMCLIENT. Но точный формат нужен, чтобы понять, можно ли передать blob произвольного размера.

5. **Thread safety** — `client_obj` глобальный. Если два потока одновременно вызовут `F_SendGenCmdDataToServer`, PMCLIENT сериализует, или будет гонка? Это определяет, нужен ли мьютекс в `GpiDispatch` вокруг пары send/recv.

6. **`F_RecvDataFromServer` — блокирующий?** С таймаутом? Что возвращает при разрыве соединения?

7. **`F_SendCmdToServer` vs `F_SendGenCmdToServer`** — в чём разница? Первая — fire-and-forget, вторая — с ожиданием ответа? Или обе fire-and-forget, а ответ всегда через `F_RecvDataFromServer`?

Ранее я предлагал TCP-транспорт с `RecvAll`/`SendAll`. **Это отменяется.** Клиент использует PMCLIENT.DLL, framing и переподключение — внутри PMCLIENT. `GpiDispatch` вызывает `F_SendGenCmdDataToServer` (или эквивалент) и, если нужно, `F_RecvDataFromServer`. Никаких сокетов в PMGPI.DLL.

TCP остаётся только на серверной стороне (Фаза G, PAL) — если PMCLIENT.DLL на Windows-сервере использует TCP, а на OS/2 — PMPIPE, это внутреннее дело PMCLIENT. PMGPI.DLL транспорт-агностичен.

## 1.5. `[GOCA]` GPI построен на GOCA — что это меняет

В оригинальной OS/2 `Gpi*` в режимах retain / draw-and-retain не рисуют пиксели напрямую, а **генерируют графические ордера** (GOCA orders, `OCODE_*` из `<pmord.h>`) и сохраняют их в сегменте. `GpiPutData`/`GpiGetData` — штатный интерфейс обмена этими ордерами. `pmord.h` содержит структуры ордеров.

Следствия для этой архитектуры:

1. **GOCA — внутренний язык GPI, а не внешний формат.** Использовать ордера в протоколе — не изобретение, а восстановление исходного интерфейса GPI/GRE.

2. **Схема § 1 — отправная точка (тонкий клиент).** На сервере PMGPI принимает `F_CMD_GPI_DISPATCH`, вызывает `Gpi*`, тот генерирует ордер и отдаёт его в `GpiPutData` → PMGRE. Клиент — только прокси. **Это фазы 1–3 плана.**

3. **Цель — модель A (толстый клиент).** PMGPI (GPI-ядро: state machine, генерация ордеров, сегменты, запросы) переезжает на клиент. Сервер оставляет `GpiPutData`-интерпретатор и PMGRE. Протокол сужается до lifecycle + `PUT_ORDERS`. **Это фаза 6.5 плана.**

4. **`GpiPutData`-интерпретатор на сервере stateful.** `OCODE_GCLINE` рисует текущими атрибутами; `OCODE_GSCA` меняет атрибут. Поток ордеров строит состояние PS. «Stateless passthrough» — неверно; сервер держит состояние в любом случае, меняется только его объём (в тонкой фазе — полный GPI, в толстой — состояние рендера).

5. **Per-function маршалинг — расходный материал.** Он работает в тонкой фазе (фазы 1–5), в модели A заменяется на `PutOrder`. Логика остаётся в GPI-ядре, а не в обёртке.

6. **`GpiQuery*` в модели A — локально на клиенте.** RPC для них исчезает. В тонкой фазе — через `F_CMD_GPI_DISPATCH` как сейчас.

## 3. Границы

**GPI прокидывается, GRE — нет.** Клиент шлёт высокоуровневые `Gpi*` (`F_CMD_GPI_DISPATCH`), сервер сам превращает их в `Gre*`. Клиент не знает про `Gre*`, `F_DC`, растеризатор.

**`[GOCA]` В модели A клиент шлёт не `Gpi*`, а GOCA-поток (`F_CMD_PUT_ORDERS`).** Сервер не знает про `GpiLine`/`GpiSetColor` — только `OCODE_GCLINE`/`OCODE_GSCA`. Граница проходит по `GpiPutData`/`GpiGetData` — естественный интерфейс обмена ордерами.

**WndProc не прокидывается.** Стандартные — тонкий прокси в PMMERGE → `F_CMD_CTL_PROC` → серверный `Server*WndProc`. Кастомные — локально на клиенте.

**Win\* API прокидывается.** `F_CMD_WIN_*`, сервер управляет `pWND[]`.

# Часть II. Протокол

## 4. Транспорт

**OS/2-клиент:** `PMCLIENT.DLL` (`pmclient.h`). Framing и переподключение внутри PMCLIENT. Клиент PMGPI не знает про сокеты.

**Сервер:** pluggable через `pal_transport_*`:
- `pal_transport_pipe.c` — PMPIPE на OS/2, named pipe на Windows, Unix socket на Linux.
- `pal_transport_tcp.c` — TCP loopback, для отладки и remote-клиента.

**MVP:** PMPIPE через PMCLIENT на OS/2, TCP loopback на сервере, если сервер не на OS/2.

## 5. Формат сообщений

Все сообщения — **заголовок + опциональный payload**. Порядок байт — native (LE для MVP). BE-нормализация — отдельная задача.

```c
struct FPM_MSG_HEADER {
    ULONG   ulCommand;   /* F_CMD_* */
    ULONG   ulHandle;    /* HPS/HDC/HWND/HAB/... (зависит от команды) */
    ULONG   cbPayload;   /* размер payload в байтах */
    ULONG   ulFlags;     /* зарезервировано, 0 */
};
/* payload следует за заголовком, cbPayload байт */
```

Ответ:

```c
struct FPM_RESP_HEADER {
    ULONG   ulStatus;    /* 0 = ok, иначе PMERR_* или APIRET */
    ULONG   ulResult;    /* возвращаемое значение (LONG/BOOL/HANDLE) */
    ULONG   cbPayload;   /* размер payload (например, для Query*) */
    ULONG   ulLastError; /* per-connection last error */
};
```

## 7. `F_CMD_GPI_DISPATCH` — generic dispatcher для `Gpi*`

Аналог `Gre32EntryN`. Одна команда для всех `Gpi*`. Код функции — в payload.

**Запрос:**
```
HEADER: command=F_CMD_GPI_DISPATCH, handle=hps, cbPayload=sizeof(FPM_GPI_CALL)+cbArgs
payload:
  struct FPM_GPI_CALL {
      ULONG   ulFnCode;    /* N_GpiLine, N_GpiSetColor, ... */
      ULONG   cbArgs;      /* размер упакованных аргументов */
      ULONG   ulFlags;     /* зарезервировано */
      BYTE    abArgs[];    /* упакованные аргументы (см. ниже) */
  };
```

**Ответ:**
```
HEADER: command=F_CMD_GPI_DISPATCH, status=0
payload:
  ULONG   ulResult;   /* LONG/BOOL/HANDLE — приводится к ULONG */
  ULONG   ulLastError;/* PMERR_* если статус != 0 */
```

**Коды функций (`gpi_wire.h`):**

```c
#define N_GpiLine              0x0001

Указатели на клиентские данные **не передаются** — передаётся содержимое.

**Почему не per-function команды:** протокол не растёт с каждой функцией. Enum команд остаётся постоянным. `switch` локализован в `DispatchGpi` (сервер) и в `GpiDispatch` (клиент).

## 7.5. `[GOCA]` `F_CMD_PUT_ORDERS` — модель A (фаза 6.5)

После миграции GPI-ядра на клиент рисующие `Gpi*` не пересекают провод как вызовы. Клиент эмитит GOCA-ордера в буфер PS и отправляет батчем.

**Запрос:**
```
HEADER: command=F_CMD_PUT_ORDERS, handle=hps, cbPayload=cbOrders
payload:
  BYTE abOrders[cbOrders];   /* GOCA-поток (OCODE_* из pmord.h) */
```

**Ответ:**
```
HEADER: command=F_CMD_PUT_ORDERS, status=0
payload:
  ULONG   ulProcessed;   /* число обработанных байт */
  ULONG   ulLastError;
```

**Серверная реализация:** `GpiPutData(hps, DFORM_NOCONV, &cbOrders, abOrders)`. Внутри — stateful-конвертер ордеров в `Gre*`.

**Инварианты потока ордеров** (важны для корректности модели A):

1. **Клиент эмитит все изменения состояния в поток**, включая атрибутные ордера в immediate-режиме. `GpiSetColor` в immediate-режиме в монолитной OS/2-логике не порождает ордер; для самодостаточного потока обязан. `retain/immediate` остаётся клиентской бухгалтерией сегментов, на провод не влияет.

2. **Порядок ордеров критичен.** Нарезка батчей (ограничение `GpiPutData` ~64 КБ, `PMERR_DATA_TOO_LONG`) должна сохранять порядок и не разрывать поток между атрибутным и рисующим ордером.

3. **Self-contained поток, не self-contained ордер.** Каждый батч начинается в известном состоянии (что следует из последовательной отправки). Сервер не «угадывает» — держит состояние непрерывно.

4. **Возврат.** `GpiPutData` возвращает число обработанных байт или `GPI_ERROR`. Прокси отображает: успех, если обработано ровно `cbOrders`.

5. **Два состояния — клиентское и серверное — совпадают по смыслу.** Клиентское — для запросов и решений о генерации; серверное — для рендера. Рассинхронизация возможна только при неполном потоке. Отсюда инвариант 1.

## 8. `F_CMD_CTL_PROC` — generic dispatcher для `WndProc`

Аналог `somDispatch` в DSOM. Одна команда для всех стандартных `WndProc`.

**Запрос:**
```
HEADER: command=F_CMD_CTL_PROC, handle=hwnd, cbPayload=sizeof(FPM_CTL_CALL)
payload:
  struct FPM_CTL_CALL {
      ULONG   msg;
      MPARAM  mp1;
      MPARAM  mp2;
  };
```

**Ответ:**
```
HEADER: command=F_CMD_CTL_PROC, status=0
payload:
  MRESULT mres;
  ULONG   ulLastError;
```

**Сервер:**
```c
case F_CMD_CTL_PROC:
    F_RecvDataFromClient(obj, &call, &len, sizeof(call));
    mres = DispatchToServerWndProc(pWND[hwnd].class, hwnd, call.msg, call.mp1, call.mp2);
    SendResponse(obj, mres, ...);
```

`DispatchToServerWndProc` — `switch (pWND[hwnd].class)`:
```c
switch (class) {
case WC_STATIC:      return ServerStaticWndProc(hwnd, msg, mp1, mp2);
case WC_BUTTON:      return ServerButtonWndProc(hwnd, msg, mp1, mp2);
case WC_ENTRYFIELD:  return ServerEntryFieldWndProc(hwnd, msg, mp1, mp2);
case WC_FRAME:       return ServerFrameWndProc(hwnd, msg, mp1, mp2);
case WC_TITLEBAR:    return ServerTitleBarWndProc(hwnd, msg, mp1, mp2);
case WC_MENU:        return ServerMenuWndProc(hwnd, msg, mp1, mp2);
/* ... */
default:             return ServerGenericDefWindowProc(hwnd, msg, mp1, mp2);
}
```

## 9. `F_CMD_SUBCLASS_CALL` — override

Когда приложение вызвало `WinSubclassWindow(hwnd, MyProc)` для стандартного контрола, сервер при каждом сообщении для `hwnd`:

1. Если `pWND[hwnd].fOverride` — шлёт клиенту `F_CMD_SUBCLASS_CALL` с `(hwnd, msg, mp1, mp2)`.
2. Клиент вызывает `MyProc`, получает `mres`.
3. Клиент возвращает `(mres, handled_flag)`:
   - `handled = TRUE` — сервер использует `mres`, стандартную обработку не запускает.
   - `handled = FALSE` — сервер использует свой `mres` от `Server*WndProc`, клиентский `mres` игнорирует.

**Запрос (сервер → клиент):**
```
HEADER: command=F_CMD_SUBCLASS_CALL, handle=hwnd
payload: FPM_CTL_CALL { msg, mp1, mp2 }
```

**Ответ (клиент → сервер):**
```
HEADER: command=F_CMD_SUBCLASS_CALL
payload: struct { MRESULT mres; ULONG fHandled; }
```

**Стоимость:** 1 IPC на сообщение для overridden контрола. Для не-overridden — 0.

## 10. `F_CMD_DEFWINDOWPROC`

`WinDefWindowProc(hwnd, msg, mp1, mp2)` на клиенте → `F_CMD_DEFWINDOWPROC` → сервер:

```c
case F_CMD_DEFWINDOWPROC:
    F_RecvDataFromClient(obj, &call, &len, sizeof(call));
    if (IsStandardClass(pWND[hwnd].class))
        mres = DispatchToServerWndProc(pWND[hwnd].class, hwnd, msg, mp1, mp2);
    else
        mres = ServerGenericDefWindowProc(hwnd, msg, mp1, mp2);
    SendResponse(obj, mres, ...);
```

**1 IPC.** Приложение, чей `MyButtonProc` вызывает `WinDefWindowProc` для необработанных, получает цепочку к `ServerButtonWndProc` через сервер. Семантика OS/2 сохранена.

## 11. `F_CMD_SET_OVERRIDE`

`WinSubclassWindow(hwnd, MyProc)` на клиенте:
1. Локально: `pOldProc = windows[hwnd].WndProc; windows[hwnd].WndProc = MyProc`.
2. 1 IPC: `F_CMD_SET_OVERRIDE` с `hwnd` → сервер ставит `pWND[hwnd].fOverride = TRUE`.

`WinSubclassWindow(hwnd, original)` (отмена):
1. Локально восстановить `WndProc`.
2. 1 IPC: `F_CMD_SET_OVERRIDE` → `pWND[hwnd].fOverride = FALSE`.

## 12. `F_CMD_WIN_GETMSG`

Клиент: `WinGetMsg(hab, &qmsg, 0, 0, 0)`.
Запрос: `F_CMD_WIN_GETMSG`, `handle=ihab`.
Ответ (если есть сообщение): `QMSG` в payload, `status=0`. Если нет — `status=PMERR_NO_MSG`, `cbPayload=0`.

**Блокирующий vs неблокирующий:** `WinGetMsg` без `PM_REMOVE` — peek; с `PM_REMOVE` — блокируется до появления сообщения. Для MVP — **неблокирующий**: клиент сам крутит цикл `WinPeekMsg` + sleep. `WinGetMsg` = `WinPeekMsg` + retry. Позже — блокирующий через `poll`/`select`.

## 13. `F_CMD_WIN_BEGINPAINT` / `F_CMD_WIN_ENDPAINT`

**BeginPaint:**
```
Клиент: WinBeginPaint(hwnd, &ps) → F_CMD_WIN_BEGINPAINT, handle=hwnd
Сервер: 
  hps = GpiCreatePS(NULL, pWND[hwnd].hdc, &sizl, 0);   // PMGPI
  GpiAssociate(hps, pWND[hwnd].hdc);
  /* clip = update region */
  GpiSetClipRegion(hps, ...);                          // PMGPI
  ответ: HPS в payload
```

**EndPaint:**
```
Клиент: WinEndPaint(&ps) → F_CMD_WIN_ENDPAINT, handle=hps
Сервер:
  GpiDestroyPS(hps);                                    // PMGPI
  /* перерисовать: blit pVBuffmem → screen */
  pal_driver_blit(...);
  ответ: status
```

**Ключевое:** сервер рисует в `pVBuffmem` (через `F_DC.pTarget`), `WinEndPaint` делает blit. Клиент не рисует — только шлёт `Gpi*` через `F_CMD_GPI_DISPATCH` (тонкая фаза) или `PUT_ORDERS` (модель A).

## 14. Обработка ошибок

**На сервере:** `WinSetErrorInfo(err)` (osFree) → compat shim → `pal_set_error(pConn, err)` → `pConn->lastError`.

**В ответе:** `FPM_RESP_HEADER.ulLastError = pConn->lastError`.

**На клиенте:** `WinGetLastError(hab)` возвращает `errorState.lastError`, который клиент обновляет из `ulLastError` каждого ответа.

**Семантика:** per-connection, не глобальная. Каждый клиент видит свои ошибки.

## 15. Endianness

**MVP:** обе стороны — little-endian (x86/x64/ARM-LE). Нормализация не делается.

**Позже:** `pal_htonl`/`pal_ntohl` в сериализаторах, wire-формат — network byte order.

# Часть III. Прокси

## 16. Gpi* прокси (`pmgpi/client/F_GPI.cpp`)

Per-function stubs, генерируются из `pmgpi.h`. Каждый stub упаковывает аргументы и вызывает `GpiDispatch`.

```c
/* Общий диспетчер */
static ULONG GpiDispatch(HPS hps, ULONG ulFnCode,
                         const void *pArgs, ULONG cbArgs)
{
    struct { ULONG ulFnCode; ULONG cbArgs; ULONG ulFlags; } call = {
        ulFnCode, cbArgs, 0
    };
    F_SendCmdToServer(client_obj, F_CMD_GPI_DISPATCH, (ULONG)hps);
    F_SendDataToServer(client_obj, &call, sizeof(call));
    if (cbArgs) F_SendDataToServer(client_obj, pArgs, cbArgs);
    struct { ULONG ulResult; ULONG ulLastError; } resp;
    F_RecvDataFromServer(client_obj, &resp, &len, sizeof(resp));
    errorState.lastError = resp.ulLastError;
    return resp.ulResult;
}

/* Сгенерированные stubs */
LONG F_GpiLine(HPS hps, PPOINTL pptl)
{
    POINTL pt = *pptl;
    return (LONG)GpiDispatch(hps, N_GpiLine, &pt, sizeof(pt));
}

BOOL F_GpiSetColor(HPS hps, LONG lColor)
{
    return (BOOL)GpiDispatch(hps, N_GpiSetColor, &lColor, sizeof(lColor));
}

BOOL F_GpiBox(HPS hps, LONG lControl, PPOINTL pptl, LONG lHRound, LONG lVRound)
{
    struct { LONG lControl; POINTL pt; LONG lHRound; LONG lVRound; } args = {
        lControl, *pptl, lHRound, lVRound
    };
    return (BOOL)GpiDispatch(hps, N_GpiBox, &args, sizeof(args));
}

LONG F_GpiCharStringAt(HPS hps, PPOINTL pptl, LONG lCount, PCH pchString)
{
    /* переменный размер: POINTL + LONG + cch + строка */
    ULONG cb = sizeof(POINTL) + sizeof(LONG) + (ULONG)lCount;
    PBYTE buf = alloca(cb);
    memcpy(buf, pptl, sizeof(POINTL));
    memcpy(buf + sizeof(POINTL), &lCount, sizeof(LONG));
    memcpy(buf + sizeof(POINTL) + sizeof(LONG), pchString, (ULONG)lCount);
    return (LONG)GpiDispatch(hps, N_GpiCharStringAt, buf, cb);
}
```

**Генератор** (`tools/gen_proxies.py`):
1. Парсит `pmgpi.h` — прототипы `Gpi*`.
2. Для каждой функции генерирует `N_GpiXxx` в `gpi_wire.h` и stub в `F_GPI.cpp`.
3. Для структур (`POINTL`, `RECTL`, `FIXED`) — генерирует сериализаторы.
4. Для функций с `PBYTE`/`PCH` — генерирует упаковку с длиной.

**Не генерируются:** `GpiCreatePS`, `GpiDestroyPS`, `GpiAssociate` (особые, см. ниже), `GpiGetData`/`GpiPutData` (переменный размер, но генерируются с кастомным marshaling).

- `INCL_DEV` — `DEV*` типы (`HCINFO`, `PHCINFO`, `PDRIVDATA`, `DEVOPENSTRUC`) и `Dev*` прототипы из `<pmdev.h>`.
- `EXTERN = extern "C"` — C-linkage при C++.

**Win32-ветка:** все типы локально. Дополнительно нужны `PDEVOPENDATA = PSZ *`, `DRIVDATA`/`PDRIVDATA`, `HCINFO`/`PHCINFO`, `STR16/32/64`/`PSTR16/32/64`, `Dev*` прототипы — дословно из `pmdev.h`.

**Единые сигнатуры для обеих платформ.** `Dev*` в `gpi_manual.cpp` — сигнатурами из `pmdev.h`, без замены `H*`-типов на `ULONG` (под OS/2 `H*` = `unsigned long`, под Win32 `H*` = `void*`; `ULONG` не подставляется).

**`FPM_UNDOC_STUB` и 14 `Gpi*`-placeholder'ов** — все определения с `EXTERN`, иначе mangling.

## 28.5. `[GOCA]` Фаза 6.5. Переход к модели A (P1, 2–3 недели)

После того как тонкий клиент работает end-to-end (фазы 1–6):

- **Перенос GPI-ядра на клиент.** `gpi32*.c`, `gpi16*.c`, `ps.c`, `segments.c` — компилируются в клиент. Тот же код, другая единица сборки.
- **Замена `GpiDispatch` на `PutOrder`** для рисующих функций. `Gpi*` генерирует ордер в `PS.ordersBuffer`; flush → `F_CMD_PUT_ORDERS`.
- **Запросы (`GpiQuery*`) — локально.** RPC для них исчезает.
- **Сервер:** `F_CMD_GPI_DISPATCH` больше не используется. `F_CMD_PUT_ORDERS` → `GpiPutData` → stateful-интерпретатор → `Gre*`.
- **Атрибутные ордера в immediate-режиме.** `GpiSetColor` эмитит `OCODE_GSCA` всегда, `retain/immediate` — клиентская бухгалтерия.
- **Lifecycle PS/resources остаются RPC** (`F_CMD_WIN_BEGINPAINT`/`ENDPAINT` продолжают работать, но `GpiCreatePS` внутри них может быть локальным, если PS уже создан).

**Выход:** клиент содержит полный GPI, сервер — stateful-интерпретатор ордеров и растеризатор. Протокол сузился до lifecycle + resources + PUT_ORDERS.

## 29. Фаза 7. Тестирование (P0, параллельно)

- Кросс-платформа: Linux, OS/2, Windows.

## 32. Риски

| Риск | Митигация |
|---|---|
| `GpiCreatePS` игнорирует `flOptions` (osFree) | Фаза 0 или отложить; для MVP — normal/pels/short/assoc |
| `unimplemented()` лжёт про успех для `BOOL` | Фаза 0 — разделить на `_bool`/`_long`/`_handle` |
| Дублирование `_db_print` | `unimpl.c` вызывает внешний `_db_print` (из `F_debug.cpp`) |
| `HPS` aliasing | Документировать; generation counter отложен |
| Растеризатор — большой объём | MVP: линии, боксы, маркеры; дуги/текст — позже (SDL_ttf или GD) |
| Кросс-платформенные баги | CI на Linux + OS/2 + Windows, ASan/Valgrind |
| `WinGetMsg` блокирующий | MVP — неблокирующий (`WinPeekMsg` + sleep); позже — `poll`/`select` |
| Endianness | MVP — LE; позже — нормализация |
| SDL на OS/2 | Отдельный `pal_driver_pm.cpp` для OS/2 |
| 16-битный ABI | Отложен; сервер не зависит |
| **`[GOCA]` Рассинхронизация CP при неполном потоке** | § 7.5, инвариант 1: клиент эмитит все изменения состояния |
| **`[GOCA]` Разрыв батча между атрибутом и рисующим ордером** | § 7.5, инвариант 2: резать только по границам ордеров |
| **`[GOCA]` Двойной CP при ошибке в середине потока** | § 7.5, инвариант 4: клиент обновляет CP после ответа для `GCCHST`/`GCPARC`/`GCFARC`; оптимистично для `GCLINE`/`GCMRK`/`GSCP` |

## 33. Что не делаем

- **Не модифицируем osFree PMGPI** (кроме багфиксов Фазы 0).
- **Не тащим GPI-логику в клиент в фазах 1–5** — она там появится в фазе 6.5.
- **Не делаем generation counter.**
- **Не делаем канонический GOCA** (внутренний round-trip работает).
- **Не делаем 16-битный ABI** до Фазы 8.
- **Не реализуем метафайлы, регионы, клип, шрифты, палитры, DDE, clipboard, atom tables, hooks, seamless** до MVP.
- **Не используем GD для линий/боксов** (свой растеризатор); GD/SDL_ttf — только для текста/дуг, если понадобится.
- **Не портируем клиент** на другие ОС (это отдельный большой проект — OS/2-загрузчик, VIO, KBD, DOSCALLS-эмуляция).

# Итог

**Архитектура (тонкая фаза 1–5):** PMGPI + PMGRE + PMWIN-менеджер + стандартные WndProc — на сервере. Gpi*-прокси + Win*-прокси + WndProc-прокси + 16-bit thunks — на клиенте. PAL — между сервером и ОС. Транспорт pluggable (PMPIPE через PMCLIENT на OS/2). Драйвер pluggable (SDL MVP).

**`[GOCA]` Архитектура (модель A, фаза 6.5):** GPI-ядро (state machine, генерация ордеров, сегменты, запросы) — на клиенте. PMGRE (stateful-интерпретатор ордеров, растеризатор) + PMWIN + WndProc — на сервере. Граница — `GpiPutData`/`GpiGetData`.

**Протокол:** конверт `FPM_MSG_HEADER`/`FPM_RESP_HEADER` стабилен. Команды: `F_CMD_GPI_DISPATCH` (тонкая), `F_CMD_PUT_ORDERS` (модель A), `F_CMD_CTL_PROC`, `F_CMD_SUBCLASS_CALL`, `F_CMD_DEFWINDOWPROC`, `F_CMD_SET_OVERRIDE`, `F_CMD_WIN_*`. Протокол не растёт с числом функций.

**Прокси:** per-function stubs для `Gpi*` — расходный материал (генерируются, заменяются на `PutOrder` в фазе 6.5). `PROXY_WNDPROC` для стандартных WndProc. Per-function `F_Win*`. 16-bit thunks — Фаза 8, только клиент.

**План:** 0 → 0.5 → 1 → 2 → 3 → 4 → 5 → 6 → **6.5** → 7 → 8. MVP — 5–6 месяцев, с моделью A — 6–7, полный — 8–9.

**Модель:** OS/2-архитектура GPI/GRE. Тонкая фаза — прокси на клиенте, полный GPI на сервере. Модель A — GPI-ядро на клиенте, GRE на сервере, `GpiPutData` как граница. ABI совместим с OS/2 на уровне символов и сигнатур.
